造城九阶
从一块砖到一座会自己营收的城

你缺的不是知识，是坐标。当你能说出「这是第几阶的问题」，需求就已经能被执行；当你说不出，再强的模型也只能猜。 这张图把编程语言到收款到账，压成九阶——前六阶是系统的名词（由什么构成），后三阶是系统的动词（如何诞生与存活）前六阶是「城里有什么」，后三阶是「这座城怎么开张、怎么做买卖」。

01全栈不等于全写。全栈是能在任意一层定位问题，并把需求翻译成那一层的语言。全栈不是一个人砌完所有墙，而是知道哪面墙出问题该找谁、该怎么说。
02AI 把「写」的边际成本压到接近零，把「说清楚」与「验收」的边际成本抬到最高。营造队不要工钱了，但图纸得你画、交房得你验。
03因此本图不是术语清单，是一张双语对照表：左边是你想看到的效果，右边是工程上可执行、可验收的说法。所以这张图是「翻译手册」：把「我想要那种感觉」，翻成施工队听得懂的话。

卷一 / 城图

九阶：一座城的剖面

把「全栈」竖起来看，它是一座楼： 下层提供约束，上层提供价值；下层出错是坍塌，上层出错是没人来。 楼下的管道漏水，楼上装修再贵也没人住；楼上的招牌不亮，楼下的功夫全白费。 前六阶是结构（系统由什么构成），后三阶是过程（系统怎么诞生、开张、活下去）。

读图
三步用这张图
① 先在下表点一层，看「它管什么 / 坏了什么症状 / 你至少要会说哪句话」——建立直觉； ② 再到对应「阶」读完整内容与图示——建立结构； ③ 描述需求卡住时，去需求译法查一句可直接用的话，或到术语词典搜词。

1.1点一层，看它管什么

右侧的百分比是编者判断，不是行业标准。它只回答一个问题：这一层的问题，能不能一句话交给 AI 而不出事。这一层的事，能不能放心全交给营造队，自己不用懂。

卷一 / 坐标

你说的「感觉」，落在哪个象限

同一个「不对」，可能属于四个完全不同的象限。判断错象限，就会得到错方案—— 把性能问题当审美问题改样式，是最常见的浪费。 明明是水管压力不够，却在重新刷墙。

Ⅰ · 看得见 × 近用户
可用「样式 / 状态 / 交互 / 布局」四类词描述。说清「触发条件 + 对象 + 变化 + 时长」就能落地。这是门面：样子、颜色、点下去的反应。最好说，也最容易被过度关注。
Ⅱ · 看得见 × 近机器
表现为日志、构建报告、部署状态。多数人在这里「看不懂但能感觉到」——因为它不给你界面，只给你文本。这是工地的施工日志：外行看不懂，出事时却是唯一证据。
Ⅲ · 看不见 × 近用户
只能用指标描述：首屏时间、交互延迟、转化率、留存。描述方式必须从「感觉」切换到「数值 + 对比基准」。这是「住进去才知道」的部分：闷不闷、吵不吵、愿不愿意再来。
Ⅳ · 看不见 × 近机器
架构、协议、数据模型、权限边界、审核规则。改一次代价最大，所以最值得在动工前用概念谈清楚。这是地基与产权：改一次要拆楼，所以必须在动工前谈。
练习
下次说「感觉不对」时，先问自己一句
「这件事，是看见了不对，还是测出来不对？」——看见的，去 Ⅰ / Ⅱ 找词；测出来的，去 Ⅲ / Ⅳ 找指标。一句话就能把方案范围砍掉一半。
卷二 · 九阶 · 结构六阶
01

砖石Language & Toolchain

结构层 · 材料学

语言只是表层。真正决定协作成本的是三件事：类型系统（静态 / 动态）、运行时（V8、Node、JVM、CPython）、以及包与构建工具链（npm、Vite、tsc）。你不必会写，但必须知道「这份代码跑在哪、怎么变成能跑的东西」。

砖石有砖、木、钢、混凝土，选哪种料取决于要盖什么。但更关键的不是料本身，而是谁把它砌起来、用什么机器切割、最后怎么运到工地——这三件事，就是编译器、打包器和运行时。

对描述能力而言，这一层的价值只有一个：分辨报错发生在哪个阶段。语法错误在转译期，依赖冲突在安装期，白屏在运行期，样式错乱在渲染期。说不出阶段，就只能把整段报错丢给 Agent，任它猜。

对你有用的只有一件事：知道毛病出在哪个车间。窑里烧坏了（语法）、料没到（依赖）、砌到一半塌了（运行）、还是装修贴歪了（渲染）——说清车间，师傅才不用把整栋楼拆开找。

过去
每种语言各配一套环境，样板与配置手写，环境问题靠经验猜。
现在
一句话说明场景，Agent 选栈并生成脚手架与配置；环境由容器/云抹平。
不变
「这套栈能不能撑住我的场景」只有你能判断。选型错误的代价，AI 不承担。
02

立面Frontend & Interface

结构层 · 门面与机关

前端是三种东西的合成：结构（HTML / DOM 树）、样式（CSS 级联与布局）、行为（JS 事件与状态）。现代工程在其上又加了两层抽象：组件化（可复用单元 + 输入输出契约）与渲染策略（CSR / SSR / SSG）。你描述「效果」时，本质是在描述一个映射：状态 → 视图。

立面是别人第一眼看到的东西：墙体（骨架）、涂料与门窗（样式）、水电与机关（交互）。门面好看不等于房子好住，但没有门面就没有客人。而所谓「组件」，就是同一款窗框可以先做一批、再装到一百个房间。

描述界面时，把一句话拆成四段最有效：对象（哪个元素）＋ 触发（什么条件）＋ 变化（哪些属性）＋ 时长与缓动（多少毫秒、什么曲线）。缺哪段，Agent 就得替你猜一段；猜错的概率，与缺的段数成正比。

想让师傅做对，得说四件事：改哪个窗、什么时候动、怎么动、动多久。只说「让它灵动一点」，师傅只能自由发挥。

过去
切图、手调像素、逐个浏览器对齐；动效靠手写关键帧，一个 5 秒转场要调两天。
现在
给参考图或一句话描述，直接生成结构与样式；动效可由自然语言反复微调。
不变
审美判断、交互是否顺手、「这个效果该怎么描述才不歧义」——三件都还在你手上。
03

脏腑Backend & Data

结构层 · 市政与仓储

后端处理的是「不可见但不可错」的部分：请求生命周期（路由 → 中间件 → 业务逻辑 → 数据访问 → 响应）、鉴权与授权、数据一致性（事务、幂等）、失败处理（重试、降级、限流）。其中数据模型一旦定错，界面改十次也救不回来。

脏腑是看不见的市政：水管、下水道、配电、仓储。客人只看到水龙头出水，但决定体验的是水压和管道。而且 管道一旦埋进墙里，再改就得砸墙——这就是「数据模型」为什么要在动工前定。

易混
鉴权（Authentication）≠ 授权（Authorization）
前者回答「你是谁」（登录、Token、Session），后者回答「你能做什么」（角色、权限、数据范围）。二者常被一句「加个登录」含混带过，结果是越权漏洞。前者是验身份证，后者是看你能进哪几间房。只查身份证不查房间，就是让人拿着门票进了仓库。
过去
从零搭 CRUD、鉴权、部署，一个人做后端要两周起步。
现在
云开发 / BaaS 几分钟出后端，业务逻辑交给 Agent 写，联调由接口契约约束。
不变
数据模型、权限边界、钱与账，三样都不能试错。它们决定的是「能不能改」，而不是「好不好看」。
04

地基Server & Network

结构层 · 地皮、水电、道路

服务器只是「一台持续运行、有公网地址的计算机」，其上叠加操作系统、端口、进程与网络协议。上云之后，它被抽象成三张账单：计算（实例 / 容器 / 函数）、存储、带宽与流量。HTTPS 已是默认项，不再是加分项。

地皮、水电煤、道路。你可以租（云），不必买（自建机房）。租金按用量算，所以「能跑」和「跑得起」是两件事——很多项目不是做不出来，是养不起。

这一层最常被忽略的其实是成本结构：流量、存储、出网带宽通常是账单主角，而计算资源反而便宜。于是「图片不压缩直接上传」这种小决定，在用户量上来后会变成主要开支。

很多人以为服务器贵在「机器」，其实贵在运货：每张没压缩的图，都等于每次有人路过就重新运一遍砖。

过去
买机器、装系统、配环境、做备份，一周起步；扩容要等硬件。
现在
云 + 容器 + 基础设施即代码，几分钟起一套；按量付费，用完即停。
不变
容量与成本的估算、故障时的定位路径。云不会替你判断「这点流量值不值这个钱」。
05

门牌Domain & Address

结构层 · 门牌、邮局、导航

域名是给人看的别名，IP 是给机器用的坐标，DNS 是二者之间的电话簿，URL 是「协议 + 域名 + 路径 + 参数」的完整地址。中国内地服务器绑定域名对外提供网站服务，必须完成 ICP 备案；这一步常常比写代码更耗时，且无法由 AI 代办。

门牌号（域名）、地图坐标（IP）、邮局的查询台（DNS）、以及「走哪条路、进哪个门、找哪间房」（URL / 路径 / 端口）。备案，相当于去市政登记这栋楼真的存在——没登记，牌子挂不出去。

常识
域名、服务器、备案，是三件不同的事
域名在注册商买（使用权，按年）；服务器在云厂商租（资源，按量/按月）；备案在管局办（行政许可，跟主体和接入商绑定）。换服务器可能要变更备案，换域名则要重新备案。门牌是租的、地皮是租的、营业执照是批的。三份合同，三套期限，别当成一件事。
过去
手工配解析、手动申请证书、到期忘记续费导致全站报警。
现在
托管平台一键签发与自动续期，绑定域名即出 HTTPS；解析可由模板生成。
不变
备案与主体资质的时间成本。政策流程不能并行化，也不能由模型代跑。
06

店铺Platform & Form

结构层 · 一条街上的九种店面

同一套业务，可以做成网页、H5、小程序、原生 APP、桌面端、游戏、插件、开放 API 或 Agent。差别不在「技术栈」，而在分发渠道、系统能力边界、审核规则与抽成结构。选形态，本质是选分发。

同一种生意，可以摆摊（网页）、进商场租柜台（小程序）、开独立门店（APP）、进写字楼（桌面端）、开游乐场（游戏）、在别人店里寄卖（插件），或者只做批发不开门（API）。门面选错，客流就没了。

形态能力边界分发与门槛典型适配
网页 / 网站全平台可开，系统能力最弱搜索引擎 + 自有域名，需备案内容、工具、官网、轻交互
H5同网页，偏移动端链接即传播，无安装活动页、邀请、营销裂变
微信小程序可调微信能力（登录/支付/分享/订阅消息）微信内搜索与分享，需主体资质与审核交易、预约、会员、线下核销
原生 APP系统能力最全应用商店审核，安装成本高高频、重交互、需推送
桌面端本地文件与硬件能力强下载安装包，签名与更新自管生产力工具、批量处理
游戏渲染与实时性要求最高商店 + 买量，版号等合规前置娱乐、教育化、互动叙事
插件 / 扩展寄生于宿主能力宿主商店审核，受宿主政策约束提效工具、垂直场景增强
API / Agent无界面，能力即产品开发者接入、文档与计费被集成、自动化、MCP 服务
过去
一种形态一套人马、一套代码、一套发布流程；多端 = 多团队。
现在
一套业务逻辑 + 跨端框架 + AI 改造，多端产物可批量生成。
不变
分发规则与审核政策，是这个层真正的门槛。代码可以生成，入口不能生成。

07

工序Engineering Workflow

过程层 · 营造法式

从想法到可运行系统，有一条固定工序：需求 → 设计 → 编码 → 版本控制 → 构建 → 测试 → 部署 → 监控 → 迭代。它的价值不是「流程感」，而是让错误在小成本处被发现。Git 的分支与提交，是这条工序的记账方式——它让你随时能回到「昨天还好的那一版」。

营造法式：先画图（需求）、再打样（原型）、再施工（编码）、每天记账（Git）、验收（测试）、交房（部署）、住进去还要维修（监控与迭代）。每一步都是为了让毛病在便宜的时候暴露。砌到三十层才发现图纸错了，代价是三十层。

术语
「部署 / 上线 / 发布 / 发行」不是同义词
部署 = 把产物放到服务器并跑起来；上线 = 对外可用；发布 = 版本生效并对外声明；发行 = 进入分发渠道（商店、平台）。四件事可以同时，也可以分四周。部署是把家具搬进屋；上线是开门；发布是挂上「今日开业」的牌子；发行是进商圈、上导览图。
过去
工序粒度由团队规模决定；小项目常常跳过设计、测试、监控。
现在
一个人也能跑完整工序：Agent 补位设计与测试，流水线自动构建部署。
不变
顺序不能省。省掉的环节不会消失，只会延迟到最贵的时刻出现。
08

开业Launch & Distribution

过程层 · 挂牌、过审、进商圈

代码跑起来只是「房子盖好」。真正对外营业要过三道闸：主体与类目资质、合规与隐私、平台审核。任何一道不过，前面的工作都停在门口。此外还有三件常被忽略的前置：备案（网站 / APP / 小程序，视形态而定）、隐私政策与用户协议、内容与支付合规。

房子盖好不等于能营业：要办执照（资质）、过消防（合规与隐私）、挂招牌（域名与上架）、进商圈（分发渠道）。开业当天还得有人来——那就是获客，属于第九阶的事。

提醒
先查类目，再动手
涉及医疗、金融、教育、食品、直播、社交等类目，通常需要额外资质或前置审批。先确认能不能上线，再决定做不做——顺序反了，代码写得再漂亮也只能停在草稿箱。规则以平台官方最新公告为准。
过去
上架要排期、要人对接、要反复改版本；资质问题常在提审时才暴露。
现在
生成即部署（静态托管 / 云开发一键），材料可由 AI 起草，审核反馈可逐条对照整改。
不变
审核与合规是主体责任，不是技术问题。AI 能帮你准备材料，不能替你承担后果。
09

营收Business & Monetization

过程层 · 收银、账房、复购

变现不是「加个支付按钮」，而是四件事的组合：谁付（客户）、为什么付（价值主张）、怎么付（支付通道与计费方式）、付完怎么持续（留存与复购）。支付只是其中一环，且牵涉资质、签名、回调、分账、退款、对账与税务。

收银台只是最后一步。真正决定能不能赚钱的是：谁进门、为什么买、买一次还是每月都买、钱怎么分给一起干的人。收银机本身，是最容易装的那个零件。

硬约束
iOS 虚拟支付的限制，先确认再开发
iOS 端对「虚拟商品 / 虚拟服务」的站内支付长期受限，涉及数字内容售卖时通常需走苹果 IAP 或平台专门通道，且涉及分成。近年平台已推出面向小程序的虚拟支付能力，但需申请、有准入与分成规则。具体政策以微信官方文档与苹果最新条款为准，不要以旧文章为依据。卖实物（茶叶、手作）和卖虚拟（课程、会员、次数包）是两条完全不同的规矩。虚拟的那条在苹果地盘上尤其严，先问清楚再动工。
过去
签商户号、写回调、自建对账；小团队常因资质与费率卡在门外。
现在
平台化接入 + 平台代收代付；面向 Agent 的原生支付通道开始出现（对话内直接下单结算）。
不变
定价与价值主张是商业判断，不是技术问题。支付能自动化，凭什么收钱不能。
卷三 / 价值链

从代码到钱：五次转换，四次损耗

代码不是产品，产品不是生意。中间隔着四次转换，每一次都有损耗率—— 多数项目的失败不在第一段（写不出），而在第二、三段（没人用、收不到钱），却把 90% 的注意力花在第一段。 多数人把力气全花在砌墙上，却没人想过：这店开在哪、谁会进来、进门之后凭什么掏钱。

路径现金流速度启动成本天花板主要风险
① 项目交付 / 商单快（预付 + 尾款）低（时间为主）受工时限制不可复用，收入随时断
② 工具订阅慢（需先有用户）中（开发 + 运维）高（边际成本低）获客成本高，留存难
③ 平台分佣 / 虚拟商品中（随流量）中（资质 + 接入）受平台规则约束政策变动、抽成、封禁
④ 资产售卖（模板 / 素材 / 课程）中低（已有积累）中（需持续上新）同质化、盗版
卷四 / 天时

AI 前后：不是变快，是换了瓶颈

把 AI 理解为「提速工具」会低估它，也会高估自己。它真正改变的是瓶颈的位置：执行环节的成本塌陷，定义与验收环节的权重上升。工序没有减少，只是每一步的人变少了。 不是「工匠变快了」，而是「工地不再需要那么多工匠，但需要一个更会画图、更会验收的人」。图纸画不清，快反而是灾难——错得更多、更快、更难查。

4.1三个位移

位移一：执行成本 → 定义成本
写代码、做图、剪片、配音的边际成本趋零；而「说清要什么」的成本不变，于是它从次要成本变成主要成本。工匠不要钱了，但图纸得你画。图纸画得含糊，省下的工钱全赔在返工上。
位移二：工序压缩，顺序不变
每一环耗时缩短，但「需求→设计→编码→测试→上线」的依赖关系不能跳过。跳过测试只是把成本推迟到线上。工期短了，但地基还是得先打。跳过验收的房子，住进去才开始塌。
位移三：护城河从「会做」到「有闭环」
当人人都能生成，稀缺的变成：真实场景、专有数据、分发渠道、付费关系。四样里没有一样是「代码能力」。当人人都能盖房，值钱的变成：地段、客源、口碑、和谁愿意月月付租金。

结论
AI 不淘汰「不会写代码的人」，它淘汰「说不清要什么、也判断不了好坏的人」
反过来说：概念密度是可以刻意训练的。训练方式不是背定义，而是每次描述后追问一句——「这句话里，还有哪个词是模糊的？」所以这张图的用法不是「读完」，而是「卡住时来查一句」。查十次，词汇就长在你身上了。
卷四 / 生态

生态全链路：当「开发—部署—变现」落在同一个院子

过去做一个小程序，要在五个平台之间搬运：编辑器、仓库、云主机、审核后台、支付商户号。每一次搬运都产生摩擦与损耗。腾讯生态近年的变化，本质是把这五段收进同一个账号体系与同一条结算链——这就是「原生全链路」的真实含义。 过去的做法是：在 A 店画图、B 店买料、C 店施工、D 店验收、E 店收钱。现在这五家开成了一个院子的五个门，出门就到。省下的不是钱，是「来回跑」。

它真正打通了什么
① 账号：一个主体身份贯穿开发、发布、收款；② 支付：小程序内可直接调起微信支付，无需自建收银链路；③ 分发：搜一搜、分享、小店、视频号共用同一套内容与交易资产；④ 客户：支付完成即可沉淀到企微与会员体系。同一个身份证，能在院里开工作室、领执照、摆柜台、收钱、发传单、记客户。
它的代价
规则单向：审核标准、类目、抽成、接口能力都由平台定义，变化不预告。技术栈被生态绑定后，迁移成本高于重写。院子里的规矩是房东定的。省了跑腿，就得接受门禁时间。
卷四 / 变现

收钱的四条管道与四种形状

变现 = 收入形状 × 支付管道 × 成本结构，三者必须互相匹配。用错管道，钱收不进来；用错形状，钱收不久；算错成本，越卖越亏。 收钱要同时想清三件事：卖什么形状（一次还是一直）、走哪条管道（谁替你收）、成本怎么走（卖得越多是越赚还是越亏）。

方向
「Agent 原生支付」为什么是新变量
当用户不再打开你的页面、而是让 Agent 代为完成一次购买，传统「页面 + 收银台」的转化漏斗就失效了。平台侧开始提供面向 Agent 的支付凭证与结算能力（如面向 AI 场景的专属卡 / AI 付产品），让「对话内成交」成为可能。它对独立开发者的意义是：把一个 SKU 变成一次可被调用的服务。具体能力与准入以微信支付、支付宝官方文档为准。以前收钱要人走到柜台；现在可能是「管家替你买」。你的店得能被管家认出来、报得出价、收得到款。

陷阱
AI 原生产品的成本结构，与传统软件相反
传统 SaaS 的边际成本趋零，所以「包月不限量」是安全的。AI 产品的边际成本随调用量线性增长（推理 token、图片/视频生成次数）。一旦「包月不限量」遇上重度用户，毛利会被吃穿。可行的做法：额度制 + 超额计费、按次定价、或对高成本能力单独定价。普通软件多来一个用户几乎不花钱；AI 产品多来一个用户就多烧一份电。包月随便用，等于请客不设上限。

卷六 / 译法

把「感觉」译成可执行的话

下面是一个对照器：输入你原本会说的话，它给出对应的术语与一句可直接发给 Agent 的表述。它不生成方案，只做词汇替换与约束补全——而这恰好是决定成败的一步。 这是「人话 → 工地话」的翻译机。翻不准不要紧，重点是看它补了哪几个空：对象、触发、变化、时长、标准。

提示：命中越具体，输出越准。没命中时，试着只输入一个关键词（如「加载」「弹窗」「支付」「审核」）。

8.1四段式：一个万能句式

「在 ［哪个位置 / 哪个元素］，当 ［什么条件］ 时，让 ［哪个属性］ 在 ［多少毫秒］ 内以 ［什么方式］ 变化；如果 ［异常情况］，则 ［怎么处理］。」

这个句式覆盖了工程实现需要的全部信息：定位、触发、属性、时长、异常。少一段，Agent 就要猜一段；猜错的部分，通常要花三轮对话才能纠回来。

对照
同一件事，两种说法
✗ 「这个按钮做得高级一点，有质感。」
✓ 「按钮常态用 #6fd6c4 描边、透明底；hover 时底色变 12% 透明度、描边加粗 0.5px，过渡 180ms ease-out；点击时缩放 0.98、80ms 回弹；禁用态整体降饱和 40%。」
前者需要三轮澄清，后者一次到位——差别不在审美，在术语与参数。
