00 / 摘要

一页看懂

三分钟。看完你就知道要花多少时间、要动几次手、值不值得。

我要写什么
一份「拿 HTML 当项目本体」的设计报告。把你这几轮的判断，固化成一套能照着做的东西：一个门面、一叠分块、发布时合成一本。人只管看和批注，不再管二十个聊天窗口。
要你做什么
读 20 分钟；点掉 6 张卡（1 张共享方案 + 5 张悬置项）；哪句话不对，直接圈出来写一句。不用逐字审，你看逻辑对不对就行。
我不做什么
不做编辑器、不做账号体系、不做实时协同。这三件都会把一个「够用的小工具」拖成「要养的软件」。这一条会贯穿全篇。
◎
这份东西本身是张样张
用鼠标选中任意一句话，会冒出「＋ 批注」按钮——点开选个类型（认可 / 否决 / 悬置 / 代议 / 补充），写一句，就进了右下角的批注篮，攒完可一键导出 JSON。这就是我们想让正式报告具备的手感，先在这儿试一次，比看十页论证管用。
01 / 病灶

一棵没人修剪的树病灶：分支树缺少结算机制

先确认我们说的是同一个病。要是病看错了，后面全是错药。 先确认诊断一致。诊断错了，方案再精巧也是错药。

1.1损耗是怎么一步步发生的

①
聊得挺顺

你和 AI 聊了几十轮，每轮它都回一篇长文。你都觉得「整体还行」。

②
没人判生死

你说过「这个先不做了」，但那句话躺在第 14 轮的一段话中间，和别的混在一起。

③
要出成果了

你把全部记录丢给 AI：「基于以上，写份报告」。

④
否掉的又活了

它把第 14 轮那段当成正经内容写了进去。因为它只看得见文字，看不见「这句已否决」。

⑤
然后你不想再碰它了

改一遍比重写还累，token 也烧得心疼。最后只捞走几份能用的文件，项目就搁那儿了。

◎
我的判断：缺的不是「总结能力」
AI 总结得再好也没用，因为聊天记录里根本没有「这条已否决」这个状态。它只有时间顺序——第几轮说了什么。时间是线性的，判断是非线性的。你需要的不是一个更聪明的总结器，是一个能装「否决」这个动作的容器。 症结不在摘要能力，而在载体缺失：会话记录只承载时序，不承载「认可/否决」这一状态位。缺少状态位，任何下游摘要在原理上都无法区分活跃与废弃内容。

1.2代价有三层，最贵的那层最难发现

钱
反复把几十轮塞进去，token 一遍遍烧。
注意力
要确认「哪条还算数」，你得从头复读一遍。
正确性（最贵）
报告引了一条早被推翻的结论。整份返工，而且往往到很后面才发现。
就在我们这轮对话里，已经攒了三条「否决」
① 把块当中间层、正文搬进 JSON（否了）· ② 配一个数据库（否了）· ③ 给效果图做实时拖拽（否了）。 如果现在你把聊天记录丢给 AI 让它总结，这三条会原样出现在正文里。这不是假设，是五分钟后就会发生的事。
02 / 本体

一个项目，一份本体本体形态：门面 + 分块 + 发布时合成

三样东西：散页、目录页、装订成册。散页是干活的，目录页是给你自己看的，装订本是给别人的。 三段式：源块（blocks）· 门面（index）· 合成品（dist）。前两者为工作态，后者为交付态。

2.1三方各管什么

角色看什么产出什么明确不管什么
你只打开门面那一页批注、拍板、点头或摇头不管底层有几个会话、上下文多长
Router（前台）门面上的「块目录」，不是聊天记录把活派给谁、汇总回答你不亲自干活，不写内容
Worker（师傅）只拿到被指派的那一块 + 相关块直接改源码，只换这一段不直接跟你说话，不碰别的块

「Router / Worker」是 DeepSeek 那篇 Super-agent 文章里的分法：一个常驻前台负责分派，一堆上下文隔离的师傅并行干活。 对你一个人来说，Router 的价值不是「同时开五个」，而是「跨天、跨设备不断线」——你隔三天回来，它还记得那块叫「竞品矩阵」。

2.2看板与连读，是同一批块的两副面孔

你选了「目录看板」，这对你自己管项目很顺手。但有个坑：客户打开看板，会不知道从哪读起。所以他看到的不该是看板。 看板为开发态视图，连读为交付态视图，共享同一批 source blocks，仅渲染顺序与导航层不同。

视图谁用 / 何时长什么样怎么产生
看板（门面）你自己，开发期卡片墙：每块一张卡，标着「摊桌上 / 收抽屉 / 贴条」和最后更新直接打开 index.html
连读（合成品）发给别人，交付期一整篇从头读到尾，块按顺序排好跑一次合成脚本
!
一句硬话：打开时拼装 = 把胶水递给读者
如果门面是「打开时才去把各块拉过来拼」，那你发给别人的就只是一个空壳，块全留在你电脑上。他打开是一片空白。所以合成必须发生在你点「发布」的那一刻，产出一个完整的单文件。 运行时 fetch 拼装会让交付物退化为一个空壳，且依赖本地服务；必须采构建期合成，产物为自包含单文件。
03 / 判据

三条尺子

这三条不是「原则」，是三把能拿来砍提议的尺子。以后谁（包括我）提出某个方案，你拿这三条一量，不合就扔。 三条判据的功能是可否决性：每条须能对应一类具体提议，并给出违反后的可观测症状。

尺一 · 交付物只有一个文件
一句话：合成发生在发布那一刻，不在别人打开的时候。

类比：散页随时改，寄出去之前装订成一本。不能让收件人自己拿胶水粘。

它挡住：打开时 fetch 拼装 · 要求对方装插件或查看器 · 交付一个文件夹

违反的症状：发出去打不开；或者对方看到的是三天前的旧块。
尺二 · 块是书签，不是中间层
一句话：AI 直接改源码，块只是给某一段贴的记号。

类比：给书里某一段贴条码贴，不是把书拆成一格一格的抽屉。

它挡住：自造一套内容格式（DSL）· 把正文搬进 JSON 模型 · 让块变成渲染单元

违反的症状：改一个字要动两处；AI 开始维护两套「真相」，然后它们对不上。
尺三 · 文件是真相，索引可重建
一句话：内容存在文件里；那个「目录清单」随时能重建，烧了也不心疼。

类比：图书馆靠卡片目录找书。卡片烧了能重抄一遍，书烧了才是真没了。

它挡住：上数据库 · 用协同编辑的二进制状态存正文 · 批注只存浏览器本地

违反的症状：换台电脑就丢状态；两本账对不上，你不知道该信哪个。
◎
为什么这三条能当尺子用
因为它们各自对应一个**我们真的讨论过、并且已经否掉**的提议：运行时拼装、块当中间层、上数据库。不能拿来否决具体提议的「原则」，都是复述。

05 / 生命周期

一块内容的一生

这一节全篇最重要。它把「书签」「判断」「只换一段」「三种去向」串成一条线——这就是你以后每天的手感。 本节将块标识、判断状态、局部替换与驻留位置合成为单条生命周期，用于验证四者在同一块 ID 上是否自洽。

5.1两个维度，不是一个

我原先只给了一个维度——「在不在眼前」。但你说得对，还差一个：这条到底算不算数。两个分开，状态才说得清。 原方案仅建模驻留维度（active/archived/tombstone），遗漏判断维度；两者正交，须分开建模后再定义合法组合。

维度一 · 判断：这条算不算数
认可——定了，就按这个走。
否决——不要了，把理由留下。
悬置——还没想好，先挂着，不许当结论用。
代议——我先不表态，授权按默认值推进，到期提醒我复核。
维度二 · 位置：在不在眼前
摊桌上——最近在用，AI 默认看得见。
收抽屉——暂时不用，说一声能取回。
贴条——确定作废，只留「为什么不行」。

两个维度怎么咬合

判断默认落在哪能不能当结论用之后怎么变
认可摊桌上能久不引用 → 收抽屉；被推翻 → 转否决
否决贴条不能，且明确标注只能显式恢复；恢复后回到「悬置」，不直接变认可
悬置摊桌上（黄色标记）不能超期未决 → 提醒；连提三次 → 建议转「代议」或「否决」
代议摊桌上（倒计时）能，但标注「暂按默认值」到期 → 转认可，或弹回悬置请你复核
为什么「悬置」是最危险的那个
它长得和「认可」一模一样：都在桌上、AI 都看得见。如果生成报告时把悬置当成了认可，就会写出「我们确定要做 X」——而 X 你根本还没想好。 所以悬置必须带标记，导出时必须单独列出来，不许混进正文。
◎
「代议」其实你已经在用了
那 6 张决策卡上写的「不选则默认 X」，本身就是一种代议——不等你想清楚，先按默认值往下走，但把它记在那儿，你随时能翻案。 把它从「决策卡的一个字段」升级成「内容的一种状态」，整套东西才自洽。

两种「收坏了」的情况

先说清一个字：下面说的「收」，都是把一块从桌上挪进抽屉，不是删掉——原话还在，只是 AI 默认不再看它。

收得太狠：三天不动就收走
你周一想到的东西，周四回来想改，发现桌上没了——得先召回才能动手。这么折腾三五次之后，你干脆把阈值调到最松，结果退回「全都留在桌上」，等于没做归档。

对症：阈值要能在用的时候随手调，且默认偏松（见 09 / Q2）。
抽屉太薄：只留名字，不留原文
三个月后你想跟人解释「当初为什么放弃方案甲」。抽屉里只有一行摘要写着「成本过高」——但你说不出当时算过什么账、对比了哪几家。这条否决就废了，下次还得重踩一遍。

对症：抽屉里必须存原文，只是不放进 AI 的默认视野。收起来 ≠ 删掉。
06 / 版本

留底与回退

这一节是上一轮漏掉的。你最早提的四条里就有它，我写的时候当成「实现细节」挤没了——不对，它是「能回退」这个承诺的地基。 本节补足版本管理维度。版本能力是「可回退」承诺的实现前提，非实现细节。

6.1先把三个东西分开

名字它到底是什么不是什么
git你电脑上的一台时光机。每保存一次，就拍一张照片，永远留着。不是云盘。它不负责让别人的电脑上也有。
GitHub把这叠照片搬到网上，别人能翻、能评论、能提修改。不是版本管理本身。只搬不拍，等于没留底。
备份另存一份，防丢。不是版本管理。备份只有「最新」，没有「第 3 版」。压缩包不算留底。
◎
你以为的「我存了很多版」，可能只是存了很多个「最新版」
「报告-最终版」「报告-最终版2」「报告-真的最终版」——这些是备份，不是版本管理。区别在：版本管理知道每一版之间改了什么，备份只知道「这是另一个文件」。

6.2三档回退，先只做第一档

档能退回什么什么时候做代价
整篇「回到上周三那一版」第一天就有，不用开发零
一节「只把竞品这一节退回旧版，别的保持现在」P1（约 2 天）要写个脚本，把一篇按块切片存快照
一句「把这句话里的『不』字改回去」不做投入产出不划算

注意第二档为什么不能靠 git 直接做到：git 是按「行」比对的，而你的报告是按「节」写的。一行跨两节、一节散在几十行，两者对不上。所以「只退一节」需要额外一层：给每块单独存快照，回退时只换那一块。 块级回退无法由行级 diff 直接支撑：HTML 的语义边界与行边界不对齐，须引入块快照层。

6.3四条约定，防止历史变成噪音

版本管理失败，十次有九次不是工具问题，是提交太乱——一次提交塞进十件事，三个月后你自己都看不懂。

01
一次提交 = 一件事

「加了一节版本管理」是一次，「顺手改了配色」是另一次。混在一起，将来想只撤其中一件就做不到。

02
提交信息写「为什么」，不写「改了什么」

「改了什么」diff 已经说了，你只需要解释当时怎么想的。三个月后救你的就是这句话。

03
分支 = 方案，不是版本号

一个分支一个问题：「要不要做实时拖拽」。定稿了打一个 tag 叫 v1。别用分支当 v1/v2/v3。

04
私人笔记不进仓库

工作日志、随手记、个人事务单独放。混进去之后，要么不敢公开，要么得回头清洗历史——两件都麻烦。

6.4仓库里放什么

放不放
源码（html-report-kit/build/）—— 能重建，必须留
成品（*.html）—— 为了开 Pages 让人直接看排版 		私人工作记忆（.workbuddy/）—— 含思考过程与个人事务
临时文件（_*.html、*.bak）—— 只是过程垃圾

6.5这个工作区已经开跑了

不用等方案定稿——现在就把这份计划书本身当第一个试验品。已经做完前两步：

提交做了什么为什么单独一次
be8e0f4基线：收录 9 份报告与工具包源码先有一个能退回的起点，后面才敢改
199950a统一换行符不统一的话，以后每次比对都显示「整篇都改了」，diff 就废了
本次加这一节版本管理内容改动，与上一条无关

看历史：git log --oneline　·　比两版：git diff be8e0f4 -- HTML本体计划书.html　·　整篇退回：git checkout be8e0f4 -- 文件名

这套东西的边界，得说在前面
整篇回退今天就能用，但「只退一节」还要等脚本（P1）。在那之前，遇到「只有第三节需要退回去」的情况，你只能整篇退——这会连带丢掉后面几节的改动。 所以别急着把大量新内容堆在一次提交里，小步提交本身就是块级回退的替代方案。
07 / 落地

五步走，每步有验收线

每步都写清「交出什么、怎么算过关、不过怎么办」。过关必须能用一条命令或一次点击判定，不能靠「感觉顺畅」。 五阶段均设可机械判定的验收条件；不满足即回到上一步，不进入下一阶段。

08 / 专门问题

评论能不能钉在位置上？ 已定 · 走 D

你问的这件事，其实是两个问题打包在一起。拆开就清楚了。 该问题可分解为锚定（anchor）与共享（shared state）两个正交子问题。

你问的真正在问什么需要什么贵不贵
评论能不能指到那一段锚定文件里就能做到：块名 + 原文摘句 + 坐标兜底免费
别人的评论能不能自动出现在我这共享必须有第三方替你们保管这里才要花钱

你要的是「别人能看」，还是「别人的意见能自动回来」？
前者免费；后者要一个信封——信封可以是导出的文件、一条链接、或一台服务器，区别只在「谁来收、多久收一次」。

这一节的判断标准，只有这一句
!
静态链接 = 打印店橱窗
谁路过都能看，但橱窗不替你收信。你发出去的页面，每个人的浏览器各存各的，评论不会自动汇总到你这里。 这不是缺陷——链接这个信道只负责「看」，不负责「协作」。想让它也负责协作，就得给它配一个信筒。 静态托管的存储是客户端本地的（localStorage / IndexedDB），无跨用户同步；共享必须引入服务端状态，这是托管模型的边界而非实现缺陷。
✓
你选了 D，我按你的定。它跟「不配数据库」是同一个思路
D 的本质是把评审交给已经存在的设施——不自己造轮子，直接借 GitHub 的 PR 评论和审批流。零开发成本，还自带留痕。但有两条得提前安排：

① GitHub 不显示网页效果，只显示代码。要让对方看到排版，得开 Pages 或另发一个预览链接，评论时对着截图说。否则对方看到的是「一堆尖括号」。
② 对方得会看 PR。如果对方不熟 GitHub，D 就退化成「只有你自己在评」，等于没共享。 D 复用仓库协作设施（PR / Review / 审批流），零自建成本；约束有二：渲染视图缺失（需 Pages 或预览链接补充），参与者需具备 Git 协作能力。

09 / 悬置

五处我拿不准

一份计划书如果不写「我哪里可能错」，那就只是推销。下面五条我给你建议，但都留了口子。你已经全部点过了（都取推荐值），想改重新点一次就行。 以下五项已按推荐值确认，保留可改；均附默认值与回退口，避免实施阶段反复请示。

Q1 · 手感开关 待定
「这块不要了，贴条」——谁说了算？
影响：这是整套遗忘机制唯一的手感开关。全自动你会不敢往里写（怕误杀），全手动就退化成今天的样子　·　不选则默认「你点头才贴」
Q2 · 阈值 待定
「摊在桌上」最多放多少块？多久不动就收抽屉？
影响：太严会找不到东西，太松则目录本身变成新负担　·　不选则默认「40 / 7 天」
Q3 · 命名 待定
每块的名字（书签）谁定？
影响：块名一改，旧的批注和版本链接就断了　·　不选则默认「AI 起名 + 你可改后锁定」
Q4 · 批注形态 待定
写批注时，要不要先选「这是什么问题」？
影响：强制分类会让批注变慢，但 AI 合并修改会更准　·　不选则默认「自由写 + AI 归类」
Q5 · 报告规模 待定
批准后那份正式报告，写多长？
影响：决定要不要上检索类组件（折叠、筛选）　·　不选则默认「6 节」

8.1如果我用最省事的方式写，会烂在哪

烂点一 · 只有「块」，没有「块不许丢」
概念正确，一用就崩。所以要配一条自检：合成前比对清单，发现少块就报错退出，不许静默合并。
烂点二 · 遗忘写成「自动」却没数字
不写阈值，三个月后还是全留着。宁可先给一个错的数字，也不要给一句正确的空话。
烂点三 · 通篇没有失败案例
全是好处，可信度打折。所以 05 末尾放了「收太狠」那条反例。
烂点四 · 把「共享」写成技术选型
一出现协议名、服务器型号，你就会跳过这一节。所以 07 只写「能做到 / 做不到 / 代价 / 何时选」。
