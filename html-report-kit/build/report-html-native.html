00 / 摘要

三句话，加三处更正

①
问题不在「记不住」，在「没结算」

会话记录里只有「第几轮说了什么」，没有「这条已否决」这个格子。所以任何下游总结都无法区分「还在用」和「早不要了」——这不是模型不够聪明，是数据里压根没存这个信息。 会话载体仅承载时序，不承载判断状态位；缺失该位，任何下游摘要都无法在原理上区分活跃与废弃内容。

②
所以「更简单的办法」都不够

窗口再大、提示词再好、检索再准，都是在提升读取能力。但问题在写入——没人把「否决」写进去。第 02 节逐条说明。 窗口扩容、提示工程、检索增强均作用于读取侧；缺陷位于写入侧，故不构成解法。

③
token 和返工，是同一量级的两笔账

我第一版把这笔账算错了一千倍（见 0.1）。按真实用量重算：一次深度会话约五千万 token、七到三十五块；一年五十个项目三五千万把块。而返工是四千多。同量级。所以不是「只省一边」，是两边都省。 重算后：单次深度会话约 50M token，折 ¥7–35；年度 token 支出 ¥0.4k–5k，与返工支出 ¥4.15k 同量级。

0.1三处更正，第一处是算错

批注里有三条直接打在这儿了：一条是算术错误，一条是我说重了，一条仍然成立。

① token 账我算错了，差三个数量级
我按「30 轮 × 每轮一次往返」估成 5 万 token。但每轮都要重发全部历史，光这一项就是 77 万（15 倍）；叠加 agent 一个 turn 内多次工具调用，实测到 5000 万量级（一千倍）。

结论整个翻过来：token 不是「不值一提」，而是与返工同量级的主成本。第 04 节重算。
② 块不是「一层结构」
我一度把它说成「加一层中间层」，听起来要维护两套东西。其实它就是一个 HTML 属性——给某段贴个名字，内容一个字没搬。

说成「层」会让人以为成本很高，其实成本接近零。
③ 「实时交互」不是过度工程，是第二阶段
我原来写成「过度工程」，太重了。实时交互是这套范式的成熟形态，只是当前 token 成本下不划算。

等成本下来、或预算充裕，就该上：内联拖拽、画布编排、原地生图。它不是被否掉，是排在后面。
01 / 机理

为什么这件事必然发生

如果只是「人懒」，那靠自律就能解决。但它不是——是三层结构问题叠在一起，所以换个更努力的人也照样发生。 该现象不可归因于执行者自律度，须从数据结构、激励结构与成本时序三层解释。

◎
先说清：这里有两种病，不是一个
病 A（跨轮）：几十轮聊下来，某条被否了但没记下来，后来又写进报告。

病 B（单篇）：一次输出的长文档里，整体读着「尚可」，但局部有矛盾、有似是而非——因为深究太费劲，当时就放过了。然后 AI 读它时默认每一句都是对的，瑕疵被当真往下传。

下面 1.1–1.3 讲的是病 A，因为它的结构原因最清楚。但病 B 更常见——它不是「忘了哪条被否」，而是「整篇都放过了」。块机制对两种都管用：它让「局部」变得可指认、可单独确认。 失效分两类：跨轮判断丢失（A）与单篇局部未校验（B）。前者源于状态位缺失，后者源于「整体可接受」的验收粒度——细粒度校验成本高于其时的收益预期，故被系统性跳过，但下游模型会将其视为等价于已校验语义。

1.1第一层：结构上没有「否决」这个格子

一段对话记录长这样：第 14 轮 · 助手：建议做方案甲，理由是……。它记了谁在什么时候说了什么，但没记「这条后来被否了」。 会话数据结构为时序序列，字段仅含角色、内容、时间，不含判断状态位。

会话记录里有的会话记录里没有的
这句话是谁说的 · 第几轮 · 原文是什么 这句话现在还算不算数 · 是被采纳还是被否 · 有没有人复核过

所以下游不管用什么模型去总结，它拿到的都是一堆「说过的话」。它没有依据去区分死活。指望它区分，等于指望它读心。

1.2第二层：系统默认奖励「继续产出」

你每问一句，它就回一大篇——反馈是即时且丰盛的。而「停下来把前面三十轮结清」这件事，反馈是延迟且枯燥的。 交互的即时奖励偏向增量产出，结算动作缺乏即时正反馈，故在无外部约束时被系统性推迟。

于是「整体尚可，先往下走」成了默认选择。这不是懒，是激励结构决定的——就像没人会主动去整理报销单，除非报销日到了。

1.3第三层：推迟结算，看起来永远划算

现在结清要打断思路、要判断、要做决定；放到最后再结，好像能省事。问题是结算成本不是恒定的——上下文越长、分支越多，判断一件事「还算不算数」就越费劲。 结算成本随上下文规模超线性上升，导致贴现后「推迟」在任一局部时点看似占优，至终点集中爆发。

所以结论是这句
缺的不是更聪明的总结器，是一个能装「否决」这个动作的容器。容器不需要智能，只需要有那几个格子，并且逼你在便宜的时候填它。 解法要素为「可写入的状态位 + 低成本的写入时机」，而非更强的摘要能力。
02 / 反方

四种更简单的办法，为什么不够

一个方案如果不能说明「为什么不用更笨的办法」，那它多半是过度设计。下面四条我都认真考虑过。 以下四项为最有可能成立的替代方案，逐一给出不成立的具体理由。

替代方案它的真实能力为什么解决不了
窗口再大点
百万级上下文		 能一次性塞进更多历史，确实不用切分 窗口变大，不会凭空产生「已否决」这个状态。塞进去的仍是一堆没标死活的文字。而且越长越容易漏看中段——这是注意力分布的实测现象，不是玄学
提示词写好点
更强的系统指令		 能约束输出格式、语气、检查清单 提示词管不住「跨轮的判断」。它能规定这一次怎么答，但没法替你记住「第 14 轮那条已经否了」。状态得住在外面的存储里，不住在提示词里
知识库 / 检索
RAG、向量库		 能按语义找回相关材料，比全文塞更省 检索只能按「相关」找，不能按「还算不算数」筛。你搜「定价方案」，它会同时捞回采纳的和废弃的——因为两者语义高度相关。相关性恰恰是最糟的筛选标准
换个更强的模型 判断力更强，更会挑重点 模型再强，也替代不了你的判断。「这个方案要不要留」是决策，不是推理。它能替你分析利弊，但那个「否」字必须有人按下
◎
四条路指向同一个盲点
它们全在「怎么把已有内容读得更好」上使劲，没有一条在「谁来写下判断」上使劲。而问题恰恰在后者。 四项替代方案均属读取侧优化，写入侧（判断落盘）无任一覆盖。

03 / 岔路口

五个岔路口，为什么这么拐

技术选型最怕的不是选错，是不知道为什么选。这里每个岔路口都写清「如果走另一条会怎样」。 每项给出被否选项及其具体失效方式，避免「选了但说不清为什么」。

岔路口走了这条没走那条走错会怎样
① 内容存哪 文件（HTML + JSON） 数据库 变成两本账。库里一份、文件里一份，一旦不同步，你不知道该信哪个。而你原本要解决的，正是「分不清哪个是真的」
② 怎么留底 git（快照式） 协同编辑的实时状态 真相变成二进制。文件从此打不开、发不了、存不了档——恰好毁掉 HTML 唯一的杀手级优势
③ 什么时候合成 发布时合成一个文件 打开时去拉各块 发出去是个空壳。对方只收到外壳，块全留在你电脑上，他打开就是白屏
④ 块是什么 源码上的一个标签 一层独立的内容结构 改一个字要动两处。内容在结构里一份、在 HTML 里一份，AI 开始维护两套真相，然后它们对不上
⑤ 共享怎么给 复用 GitHub 的评审流 自己搭一套评论后台 多一样要养的东西。账号、权限、部署、每月维护——对一个人来说，维护成本比月费贵得多
这五条有一个共同点
每一次都选了「少一样要维护的东西」那条。不是因为它更先进，是因为一个人扛不住多一样东西。技术选型的真正约束不是能力上限，是维护下限。 五项选择的共同判据为运维表面积最小化，而非能力上限最大化。
04 / 算账

把账算出来，别凭感觉

这一节是全文最实在的地方，也是最打我自己脸的地方——算完发现，我一直强调的「省 token」几乎不值一提。 本节给出 token、上下文占用、返工三项实测估算，其中第一项推翻原价值主张。

4.1token 账：我先算错了三个数量级

这一节把错误过程完整摊开，因为它是个典型陷阱，不是笔误。

算法结果差在哪
我的第一版约 5 万按「一轮一次往返」：30 × (150 + 1500)
加上历史重发约 77 万每轮都要把前面全部内容再发一遍 —— 15 倍
加上工具循环约 360–720 万一个 turn 内多次模型调用，每次都带全量上下文
实测用量约 5,000 万长文档生成 + 多轮工具调用，缓存命中约 95%

差一千倍。这不是精度问题，是把「聊天」的模型套在了「agent」上—— 聊天是一问一答；agent 是「一个人干一天活，每动一下都回头把全部资料重看一遍」。

项低价档中价档说明
单次深度会话¥7.4¥34.55,000 万 token · 95% 缓存命中 · 约 9 万输出
一年 50 项目 × 1 次¥372¥1,724
一年 50 项目 × 3 次¥1,114¥5,170深度项目通常不止一次会话
返工对照¥4,1508.3 人日 × ¥500
结论翻转：两笔账都得算
token 支出 ¥0.4k–5k，返工支出 ¥4.15k，同量级；中价档下 token 甚至更高。 所以价值主张不是「只省一边」，而是两边都省：少重跑 = 少烧 token，少返工 = 少花人力。

更要紧的是：五千万 token 的会话，注意力稀释和幻觉率也在那儿。省钱和提质，在这里是同一件事。

4.2返工账：这才是真金白银

项估算说明
一次报告返工约 0.5 人日发现引用了被否决的结论，要回溯、重写、再核
一年返工次数约 17 次按 50 个项目里 1/3 需要返工估
一年总返工约 8.3 人日这还是保守估计，没算「返工后发现又错」的二轮

4.3为什么「桌上留 40 块」

这个数字不是拍的。假设每块的摘要（标题 + 一行状态 + 关键句）约 400 token： 按每块摘要约 400 token 估算目录开销，推导阈值上限。

桌上块数目录开销占十万级窗口判断

05 / 死法

这套东西会怎么死

写方案的人有义务说清「它最可能死在哪」。下面六种死法按可能性排序，每条都给对策。 按发生概率降序排列失效模式，各附缓解措施。

#怎么死的根因对策
1 懒得批注
最常见		 逐句批注的成本高于收益。写着写着就只剩「嗯，可以」 只在节点批注，不做逐句；一个项目全程批注次数控制在 20 次以内
2 本体膨胀 块只增不减，目录本身变成新的负担 三态自动归档；超 40 块强制提示；归档可逆所以敢收
3 悬置被当成认可 两者都在桌上、AI 都看得见，生成时容易混 悬置强制带标记；导出时单独列出；报告里不许混进正文
4 块名漂移 AI 整篇重写时把 data-block 弄丢，旧批注全断 合成前比对清单，少一块就报错退出，不许静默合并
5 源与产物不一致 改了源码忘了重新构建，发出去的是旧版 构建脚本内联 + 自检；提交前跑一次，不一致就失败
6 历史变噪音 一次提交塞十件事，三个月后看不懂 一次提交一件事；提交信息写「为什么」不写「改了什么」
最该防的是第 1 条
其他五条都是技术问题，有明确解法。只有第一条是人的问题——如果批注这件事本身让你觉得麻烦，整套系统会退化成一个「好看的文件夹」。

所以设计上一直在压批注成本：选中就能批、类型可跳、攒着一起发、按 Ctrl + 回车 直接提交（不用腾出手去点按钮）。每一次交互设计上的让步，都是在跟「懒得用」抢时间。 唯一非技术失效点。系统整体价值与批注发起成本呈强负相关，故交互成本须作为一等设计约束。
06 / 判据

什么算成功，什么时候该放弃

没有判据的方案，最后都靠「感觉还行」收场。下面四条都能测，做不到就算失败。 四项指标均可量化，未达标即判定方案不成立，不以主观满意度替代。

判据目标现状基线怎么测
结算耗时 从「聊完」到「可交付」< 30 分钟 数小时到一天 记录最后一次讨论结束到报告定稿的时间戳
整合返工轮次 ≤ 1 轮 3–5 轮 数「因为引用了废弃内容而重写」的次数
块复用率 > 0，即同一块被第二个项目引用 目前为 0（每份报告从零写） 跨项目检索块名出现次数
弃用留存率 放弃项目时，可迁移资产 > 70% 只捞走几份文件，多数丢弃 项目终止时统计「被后续引用」的块占比

6.1三种情况下，应该果断放弃

项目都很短
如果绝大多数项目 3 轮就跑完，这套东西的开销大于收益。它只对「长、杂、要交付」的项目成立。
只有一个人看
如果产出从不给别人看，那「可交付」和「可评审」这两条价值直接归零，剩下的只有留底。那用 git 就够了，不必建本体。
批注始终没起来
连续三个项目，批注次数都低于 5 次——说明这套交互不合你的手。别硬撑，退回到「小步提交」也能拿到七成收益。

能写清「什么时候该放弃」的方案，才算真的方案；否则只是愿望。

— 判据先于方案，退出条件先于路线图

6.2最后一句

这套东西的本质不是「用 HTML 做报告」，是把「这条还算不算数」从你的脑子里搬到一个地方存着。HTML 只是顺手选了个既能存、又能看、又能发的载体。

所以它不需要很聪明，只需要一直在那儿、一直记着。人不擅长记这个，机器擅长。 本质是将判断状态外置为可持久化对象；HTML 因其可读、可归档、零依赖而被选为载体，非目的本身。
