本地跑 32B 的真实成本线
在哪一格

显存够不够，是入门问题；每小时有效 token 的成本才是决策问题。 这份备忘把三档硬件放在同一条时间轴上比，结论是：日更 2 小时以内，本地永远不划算；连续跑批，本地 8 个月回本。

结论一 · 显存不是瓶颈，带宽是
32B-Q4 约 19GB 权重，24G 卡放得下。但解码速度被显存带宽锁死： 单卡 1TB/s 量级只能给到 10-15 tok/s，多卡并联不会线性加速（除非张量并行切得干净）。 「能跑」和「能用来干活」之间差着一条速度线。
结论二 · 回本点是「连续占用时长」，不是「总量」
折旧按 24 个月摊，机器只要开着就在烧钱。每天用 2 小时，摊到每 token 的固定成本翻 6 倍； 连续跑批则相反，边际成本只剩电费。所以判断标准不是「我一年用多少 token」，是「机器一天开几小时」。
02 / 分档

三档硬件，三条曲线

为什么用 Q4 Q4_K_M 在 32B 上通常掉 1-3 个点，换来 40% 显存与近 2 倍速度。Q8 放不进 24G，FP16 需要 64G 以上。量化不是妥协，是选档。

03 / 证据

三份可复查的底稿

结论可以争，底稿必须能摊开。折叠起来是为了不打断阅读，不是为了藏。

证据 A · 实测记录（2026-11，本机）

模型：32B-Q4_K_M，上下文 8192，温度 0.7。测法：固定 12 条 prompt，记录首 token 延迟与解码速度，取中位数。

  • 首 token：0.9-1.4s（受 prompt 长度影响显著）
  • 解码：12.1 tok/s（单条）/ 9.4 tok/s（并发 4 条）
  • 显存占用：19.2GB / 24GB，余量不足 5GB，长上下文会 OOM

关键发现：并发 4 条时总吞吐反而更高（约 37 tok/s 合计），说明批处理能吃掉一部分带宽浪费。这条对「跑批」场景是决定性的。

证据 C · 三个失效案例（反方材料）

这三条是我推翻自己初稿的原因，单独列出：

  1. 电费被低估。满载 450W 连续跑，月电费约 160 元，占月成本的 18%，初稿按 8% 估的。
  2. 噪声与热量是隐性成本。放在卧室的方案基本不成立，等于强制加一笔「独立房间」的房租。
  3. 模型更新换不来。硬件锁死 24G，下一代 40B 级模型一出来就出局，折旧周期实际短于 24 个月。

05 / 反例

两个能推翻本文结论的条件

如果模型迭代周期缩到 12 个月
折旧周期一缩短，回本线立刻从 8 个月抬到 14 个月以上。只要出现「同样 24G 跑不动的下一代主力模型」，硬件就提前报废。 这不是概率问题，是时间问题——按过去两年的节奏，它几乎必然发生。
如果 API 价格再降 50%
本地方案的对手不是今天的 API，是六个月后的 API。硬件是买入即锁定的成本，API 是持续下降的成本。 任何「现在划算」的结论，都有半衰期。

硬件的价格是买入价，软件的价格是等待价。两条曲线交叉的地方，才是决策点。

— 本文的方法论前提，也是它最容易过期的地方
06 / 结论

落到一句可执行的话

决策
先租后买，按周验证。用云实例连续跑一周，记录真实占用时长与 token 产出； 如果日均占用 < 4 小时，直接放弃本地方案；≥ 6 小时再进采购流程。 租一周的成本，远低于买错一台机器的成本。

下一步的三个动作

01
租一周同档实例

记录日均占用时长、并发数、OOM 次数。

02
换算每小时有效 token

别算总量，算单位时间产出。

03
对照六个月后的 API 价格曲线

用趋势而不是当前价做对比。
