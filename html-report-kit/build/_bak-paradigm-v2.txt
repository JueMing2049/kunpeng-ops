<section id="v1" data-block="v2-summary" class="reveal">
  <div class="slabel">01 / 摘要</div>
  <h2>五条结论，先给判断</h2>
  <p class="slead">这一节可以独立成篇。后面每一节都是这五条的展开与证据。</p>

  <div class="steps">
    <div class="step"><div class="step__n">①</div><div><div class="step__t">强命题不成立，弱命题成立</div><p class="step__b">HTML 承载一切领域交互是错的；但「唯一同时做到人可读、机可写、可版本化、零依赖渲染的交付契约」是对的，且足够支撑全部场景。分野不在「是不是 HTML」，在<b>契约把真相放在哪</b>。</p></div></div>
    <div class="step"><div class="step__n">②</div><div><div class="step__t">四个诉求分散在四个契约层上</div><p class="step__b">批注回写是 L2，版本回滚是 L2 延伸，决策卡片是 L4，图显前置实时编辑是 L3。<b>想用一套东西兜住四件，就是在做完整 GUI。</b></p></div></div>
    <div class="step"><div class="step__n">③</div><div><div class="step__t">「实时交互」不必然导致成本攀升，「多人协作」才会</div><p class="step__b">单人单机实时拖拽约是批注方案的 2-3 倍；加入账号、权限、并发、审计后贵一个数量级（人日 → 人月）。<b>拐点在协作，不在实时。</b></p></div></div>
    <div class="step"><div class="step__n">④</div><div><div class="step__t">最锋利的参考恰恰是绕开 HTML 的那个</div><p class="step__b">EditHere 用「不依赖 DOM，屏幕上看得到就能标」反证了 <b>HTML 的通用性有域界</b>。真正全域通用的是「语义锚 + 像素锚」双轨。</p></div></div>
    <div class="step"><div class="step__n">⑤</div><div><div class="step__t">你点名的四件参考，实际是三件开源 + 一件内部能力</div><p class="step__b"><code>dsh-raw-html</code> 存在（94★）；<code>dsh-html-workbench</code> 无同名项目——<b>名字空着，建议留给你自己的插件</b>；<code>EditHere</code> 存在（228★）；WorkBuddy 人机双写是内部实现。<b>这一层还没有标准答案，谁先抽出来谁定标准。</b></p></div></div>
  </div>

  <details>
    <summary>展开：为什么第 ⑤ 条是好消息</summary>
    <div class="dbody">
      四件参考的核实结果说明，「人与 AI 之间的协商层」目前是真空：
      <code>dsh-raw-html</code> 只管渲染，<code>dsh-workbench</code> / <code>DSH-better-sidebar</code> 只管工作台与 Git，
      <code>dsh-web-design</code> 只管元素编辑回写。<b>没有一件处理「批注怎么收集、版本怎么切、决策怎么落」。</b>
      所以你不必与现存生态竞争，只需与它们组合。
    </div>
  </details>

<section id="v2" data-block="v2-thesis" class="reveal">
  <div class="slabel">02 / 命题</div>
  <h2>通用性不是来自「能画界面」，是来自「能降级」</h2>
  <p class="slead">
    2026 年有一批人在说「Markdown 已死，HTML 当立」——Anthropic 工程师的文章、中文技术圈的转述、
    以及 HtmlRAG 那类论文。这些都对，但都只说了半句。
  </p>

  <aside class="sn">
    <b>常被忽略的一点</b>
    第五行「可升级为应用」才是关键。Markdown 长不成应用，JSON 退不成文档，GenUI 会话一关就没了。只有 HTML 两头都站得住。
  </aside>

  <h3><span class="num">2.1</span>四性：HTML 真正稀缺的地方</h3>
  <div class="tbl">
    <table>
      <thead><tr><th>能力</th><th>HTML</th><th>Markdown</th><th>JSON 模型</th><th>GenUI 协议</th></tr></thead>
      <tbody>
        <tr><td>人可读（无需工具）</td><td><span class="pill p-jade">是</span> 浏览器即读</td><td><span class="pill p-jade">是</span> 纯文本</td><td><span class="pill p-red">否</span> 需渲染器</td><td><span class="pill p-red">否</span> 需宿主</td></tr>
        <tr><td>机可写（LLM 直出）</td><td><span class="pill p-jade">是</span> 训练充分</td><td><span class="pill p-jade">是</span> 最省 token</td><td><span class="pill p-cu">中</span> 易出错括号</td><td><span class="pill p-cu">中</span> 需守 schema</td></tr>
        <tr><td>可版本化（diff / git）</td><td><span class="pill p-jade">是</span> 文本行 diff</td><td><span class="pill p-jade">是</span> 行 diff 最干净</td><td><span class="pill p-cu">中</span> 需语义 diff</td><td><span class="pill p-red">否</span> 无持久产物</td></tr>
        <tr><td>零依赖渲染</td><td><span class="pill p-jade">是</span> 任何设备有浏览器</td><td><span class="pill p-cu">中</span> 需 md 渲染器</td><td><span class="pill p-red">否</span></td><td><span class="pill p-red">否</span> 绑宿主版本</td></tr>
        <tr><td>可升级为「应用」</td><td><span class="pill p-jade">是</span> 加 JS 即应用</td><td><span class="pill p-red">否</span></td><td><span class="pill p-cu">中</span> 看渲染器</td><td><span class="pill p-jade">是</span> 但不可归档</td></tr>
      </tbody>
    </table>
  </div>

  <div class="quote">
    <p>同一份文件，从「只读报告」到「可批注」到「可拖拽」到「可当应用」，是四种加载模式，不是一个产品线。</p>
    <cite>因为 Web 的原始设计哲学就是「渐进增强」——这正是 v2 这一版自身的实现原理</cite>
  </div>

  <p>
    所以「先静态批注、以后再实时」不是妥协，<b>是同一条路上往前走一格</b>。文件不用换、版本库不用迁、批注资产不浪费。
    <b>GenUI 的升级是换产品，HTML 的升级是加一层 <code>&lt;script&gt;</code>。</b>
  </p>

  <h3><span class="num">2.2</span>但通用性有域界——EditHere 教我的</h3>
  <p>
    EditHere 的 README 里有一句极清醒的话：DOM 批注（它点名了 Codex、WorkBuddy 侧栏、Agentation）
    <b>「对网页很高效，但画面一旦离开 DOM（游戏、桌面软件、视频、AI 生成的图）就无从下手」</b>。
    它把批注降到「无损原图 + 像素坐标 + 布局变更」这个更底层的契约上，于是通吃网页、Qt/WPF/Electron、手游画面、Canvas/HUD、AI 生图、视频帧。
  </p>
  <div class="card card--cu">
    <div class="card__t">由此得到一条设计法则</div>
    <div class="card__b">锚定不要只用 CSS selector。<b>语义锚（selector + 文本引用）让 AI 找得到代码，像素锚（rect + 视口）让人找得到位置。</b>两个都存，任一失效另一兜底。</div>
  </div>

<section id="v5" data-block="v2-annotation" class="reveal">
  <div class="slabel">05 / 批注层</div>
  <h2>批注要补两个维度：意图，和设计令牌</h2>
  <p class="slead">痛点不是「不能批注」——WorkBuddy 已经能了。痛点是<b>批注完 AI 只能逐条改</b>，生成一堆碎片化修订。</p>

  <h3><span class="num">5.1</span>锚定 × 意图，两个正交维度</h3>
  <div class="tbl">
    <table>
      <thead><tr><th>意图类型</th><th>典型批注</th><th>AI 的执行路径</th><th>合并策略</th></tr></thead>
      <tbody>
        <tr><td>内容纠错</td><td>「这句结论和上一节矛盾」</td><td>重写该文本块</td><td><span class="pill p-jade">合并为一次重写</span></td></tr>
        <tr><td>结构调整</td><td>「这两节顺序反了」</td><td>移动/重排块</td><td><span class="pill p-jade">合并为一次结构操作</span></td></tr>
        <tr><td>视觉调整</td><td>「表格太挤」</td><td>改 CSS / 设计令牌</td><td><span class="pill p-jade">合并为一次令牌替换</span></td></tr>
        <tr><td>补充信息</td><td>「缺一个成本数字」</td><td>需外部检索或问你</td><td><span class="pill p-cu">串行，先取数</span></td></tr>
        <tr><td>存疑待议</td><td>「这个判断我不确定」</td><td><b>不改</b>，转成决策项</td><td><span class="pill p-vi">升级为决策卡（§07）</span></td></tr>
        <tr><td>删除</td><td>「这一段不要」</td><td>删块</td><td><span class="pill p-jade">合并</span></td></tr>
      </tbody>
    </table>
  </div>
  <p><b>「存疑待议」是关键接口</b>：你截图里那张「三处需你判断」的表格，本质是 AI 把手写批注里的存疑项整理成文本；批注若自带意图，这些项可自动汇总成决策卡，不需要 AI 再写一遍。</p>

  <h3><span class="num">5.2</span>三重锚定 + 降级链</h3>
  <pre>{
  <b>"doc"</b>: "四引擎总纲.html",
  <b>"docHash"</b>: "sha256:9f2c…",        <i>// 版本对齐，防错版</i>
  <b>"block"</b>: "分野",                  <i>// 块级归属，支持局部回滚</i>
  <b>"anchor"</b>: {
    <b>"selector"</b>: "[data-block='分野'] .tbl tr:nth-child(3)",   <i>// ① 结构锚</i>
    <b>"textQuote"</b>: { "exact": "可审察上限", "prefix": "3.4.3 的", "suffix": "——" }, <i>// ② 文本锚</i>
    <b>"rect"</b>: [812, 436, 210, 24],     <i>// ③ 视觉锚（像素，跨域兜底）</i>
    <b>"viewport"</b>: [1440, 900]
  },
  <b>"intent"</b>: "structure",
  <b>"note"</b>: "这一节的表格太挤，建议拆成两张",
  <b>"priority"</b>: "should"
}</pre>
  <p><b>降级链</b>：selector → 文本模糊匹配（前后文各 32 字）→ 偏移量近似 → rect 交集 → 人工确认。
  全失败则<b>不静默丢弃</b>，而是回问「第 3 条批注找不到了，它原本指这段…还改吗？」——静默丢弃是批注系统最伤人的失败模式。</p>

  <h3><span class="num">5.3</span>设计批注要单独走令牌</h3>
  <pre>{
  <b>"intent"</b>: "design-token",
  <b>"token"</b>: "--jade",
  <b>"from"</b>: "#6fd6c4",
  <b>"to"</b>: "#7fe0cf",
  <b>"scope"</b>: ".pill--jade, .hero em, figure .darr"   <i>// 影响面先算给你看</i>
}</pre>
  <p>这样一次批注 = 一次全局令牌替换，而不是 N 处局部修补。<b>你那份 HTML 配色协调，正因为它是令牌驱动的</b>——这个优势应被批注系统利用，而不是被它破坏。</p>
  <div class="card card--jade"><div class="card__t">最小可行动作</div><div class="card__b">不重写批注 UI，只做两件事：<b>① chip 上加「这是什么问题」的速选；② 发送时按意图分组打包</b>。改动几十行，收益是「一次修订」代替「十次修订」。</div></div>
</section>

<section id="v6" data-block="v2-versioning" class="reveal">
  <div class="slabel">06 / 版本器</div>
  <h2>git 做骨，块索引做肉</h2>
  <p class="slead">难点在于：<b>HTML 是整篇文件，git 的 diff 是行级的，两者不对齐。</b></p>

  <div class="tbl">
    <table>
      <thead><tr><th>粒度</th><th>实现</th><th>能回答的问题</th><th>工程量</th><th>评价</th></tr></thead>

      <tr><td>B · 模型驱动区块</td><td>A + model schema + renderer + 属性面板（仅甘特/DAG）</td><td><b>+5-7</b></td><td><span class="pill p-jade">否</span></td><td>拖节点改边、实时校验、块级回滚</td><td>多人协作、权限</td></tr>
      <tr><td>C · 完整 GUI</td><td>B + 账号 / 权限 / 持久化 / 并发 / 审计 / 运维</td><td><b>2-3 人月</b></td><td><span class="pill p-red">是</span></td><td>一切</td><td>—（可能根本不需要）</td></tr>
    </tbody>
  </table></div>

  <div class="card">
    <div class="card__t">相对成本（滚动进入视口时生长）</div>
    <div style="font-family:var(--mono);font-size:11.5px;color:var(--txt3);margin:12px 0 4px">A 批注补丁 · 3-5 人日</div>
    <div class="bar" style="--w:8%"><i></i></div>
    <div style="font-family:var(--mono);font-size:11.5px;color:var(--txt3);margin:12px 0 4px">B 模型驱动 · 8-12 人日</div>
    <div class="bar vi" style="--w:20%"><i></i></div>
    <div style="font-family:var(--mono);font-size:11.5px;color:var(--txt3);margin:12px 0 4px">C 完整 GUI · 40-60 人日（2-3 人月）</div>
    <div class="bar red" style="--w:100%"><i></i></div>
    <p style="margin:14px 0 0;font-size:13px">A → B 是「把拖拽翻译成语义 patch」，约 2 倍成本，仍在人日量级；<b style="color:var(--red)">B → C 是多用户与权限，成本跃一个数量级</b>。你要的「实时」落在 A → B，可控。</p>
  </div>

  <div class="card card--jade"><div class="card__t">给你的判断建议</div><div class="card__b"><b>做 A + B 的一部分，明确不做 C。</b>你现在是「一个人 + 一个 AI 反复磋商」，不是「团队并发编辑」。后者的真实需求（权限、审计、冲突合并）你一个都没有，为它付一个数量级是最典型的过度设计。<b>等真的有三个人要同时改同一份报告时再说。</b></div></div>
</section>

<section id="v10" data-block="v2-roadmap" class="reveal">
  <div class="slabel">10 / 路线</div>
  <h2>五个阶段，每阶段有验收线</h2>
  <p class="slead">按你的习惯，每阶段给「产物 + 验收 + 回滚条件」。不过关不进下一步。</p>

  <div class="tbl"><table>
    <thead><tr><th>阶段</th><th>做什么</th><th>产物</th><th>验收标准</th><th>不过怎么办</th></tr></thead>
    <tbody>
      <tr><td>P0 · 1-2 天</td><td>定批注 payload schema（意图维度、三重锚定）</td><td><code>annotation.schema.json</code></td><td>手工写 5 条批注 JSON，AI 只按 JSON 修订且不误伤其他块</td><td>回 §5.2 改降级链</td></tr>
      <tr><td>P1 · 3-5 天</td><td>版本器：data-block 切片 + manifest + 块级 diff + 回滚命令</td><td><code>kb-version</code></td><td><code>rollback --block X --to vN</code> 后其余块 hash 不变</td><td>先解决生成契约，不进 P2</td></tr>
      <tr><td>P2 · 2-3 天</td><td>决策总线 + 卡片渲染器（自造 DSL，shape 照 A2UI）</td><td><code>decisions/*.json</code> + <code>&lt;kb-decision&gt;</code></td><td>3 项决策落盘；关会话重开仍能读到已决/待定</td><td>还停在消息内嵌 UI，重做存储层</td></tr>
      <tr><td>P3 · 5-7 天</td><td>只做甘特 + DAG 模型驱动（含拖拽 + 保存时 patch）</td><td><code>plan.model.json</code> + 渲染器</td><td>拖动→保存→重开位置保持；AI 改同份 model 后人的改动仍在</td><td>降级为保存时 patch，砍掉实时回写</td></tr>
      <tr><td>P4 · 3-4 天</td><td>抽成 DSH 插件三件套</td><td><code>dsh-html-workbench</code></td><td>干净 DSH 环境 <code>dsh plugin add</code> 后全流程可用</td><td>耦合没切开，回退只做脚本</td></tr>
    </tbody>
  </table></div>
  <p>合计 <b>14-21 天</b>（含 P4 工程化）；只到 P3 是 <b>8-12 天</b>，已覆盖你全部四个诉求。</p>
</section>

<section id="v11" data-block="v2-plugin" class="reveal">
  <div class="slabel">11 / 插件</div>
  <h2>如果做成 DSH 插件：只做中间层</h2>
  <p class="slead">值得做，但<b>不要做编辑器</b>——编辑器已经有三个人在做了，你做的是它们之间那道缝。</p>

  <pre><b>dsh-html-workbench</b>
├─ host/     Node 服务：文件读写 · 块索引 · 版本库(git) · 决策队列
│            通信照 dsh-workbench：HTTP + SSE 增量推送
├─ client/   浏览器 overlay：批注层 · 版本时间轴 · 决策卡渲染
│            批注层可直接复用 agentation
└─ skill/    教 AI：怎么读批注 payload · 怎么按块重写 ·
             怎么把存疑项吐成决策卡 JSON</pre>

  <h3><span class="num">11.1</span>三条边界，决定它能不能被别人组合</h3>
  <div class="steps">
    <div class="step"><div class="step__n">01</div><div><div class="step__t">不接管渲染</div><p class="step__b">复用 <code>dsh-raw-html</code>。它已经把 HTML 变界面了。</p></div></div>
    <div class="step"><div class="step__n">02</div><div><div class="step__t">不接管文件树</div><p class="step__b">复用 <code>DSH-better-sidebar</code> / <code>dsh-workbench</code> 的侧栏底座。</p></div></div>
    <div class="step"><div class="step__n">03</div><div><div class="step__t">不接管元素编辑</div><p class="step__b">复用 <code>dsh-web-design</code> 的 span rewrite。</p></div></div>
  </div>
  <p>只做<b>「人与 AI 之间的协商层」</b>：批注怎么收集、版本怎么切、决策怎么落。<b>耦合最低的插件最容易被组合；什么都做的插件，没人敢装。</b></p>
  <div class="card card--vi"><div class="card__t">命名建议</div><div class="card__b"><code>dsh-html-workbench</code> 检索无占用，但容易被误认为「又一个侧边栏」。若想更准确，可用 <code>dsh-html-review</code> 或 <code>dsh-coauthor</code>——<b>名字里带 review 或 coauthor，比带 workbench 更能说清它不是编辑器。</b></div></div>
</section>

<section id="v12" data-block="v2-critique" class="reveal">
  <div class="slabel">12 / 批判</div>
  <h2>五个还没解决的问题</h2>
  <p class="slead">只给方案不给风险是失职。以下都是我没能解决、或业界也没解决的。</p>

  <div class="grid2">
    <div class="card card--red"><div class="card__t">① 块之间的耦合</div><div class="card__b">回滚「分野」到 v5，但 v7 的「底座」引用了 v6 才有的概念——<b>引用会断</b>。要么做块级依赖声明，要么接受「回滚后人工核对」。</div></div>
    <div class="card card--red"><div class="card__t">② 块 id 的稳定性无强保证</div><div class="card__b">「保留既有 block id」只能靠生成契约 + 宿主自检。<b>自检能拦住静默损坏，拦不住 AI 真的想重构</b>，此时需要显式的「允许改结构」二次确认。</div></div>
    <div class="card card--red"><div class="card__t">③ MCP Apps 沙箱弹不出系统通知</div><div class="card__b">iframe 里没有 Notification 权限，所以「决策卡作为弹窗通知出现在大屏」<b>不能靠卡片自己实现</b>，必须走宿主侧 Decision Bus。这正是 §07 坚持总线的原因。</div></div>
    <div class="card card--red"><div class="card__t">④ 未验证项</div><div class="card__b"><code>dsh-raw-html</code> 的 VCP 规范细节未公开；A2UI 在 WorkBuddy/DSH 上的落地未实测；Agentation 与 DSH 侧栏的 iframe 兼容性未实测。<b>三项都是「看文档像可行」，没跑过。</b></div></div>
    <div class="card card--red" style="grid-column:1/-1"><div class="card__t">⑤ 「HTML 全域通用」这个说法本身要收一收</div><div class="card__b">你在提问里说「适合各个领域」，理解成「不限于某一行业」没问题；理解成「不限场景」就错了——移动端、即时通知、高频操作、需要权限的协作，HTML 都赢不了。<b>准确说法：HTML 是「思考与评审」这一横切面的通用范式，不是所有交互的通用范式。</b>把边界说清楚，方案才不会变成「什么都要做」。</div></div>
  </div>

  <div class="quote" style="margin-top:24px"><p>这一版自身就是命题的例证：同一份论点，加一层脚本，从「只能读」变成「可筛、可批、可点、可导出」。</p><cite>— 渐进增强，正是 HTML 唯一无法被替代的地方</cite></div>
</section>
