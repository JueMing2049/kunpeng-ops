00 / 摘要

五条结论，先给判断

这一节可以独立成篇。后面每一节都是这五条的展开与证据。

① 「HTML 是通用交互范式」的强命题不成立，弱命题成立
强命题（HTML 能承载一切领域的人机交互）是错的——现场操作、移动通知、高频点击它都赢不了。 弱命题（HTML 是当前唯一同时做到人可读、机可写、可版本化、零依赖渲染的交付契约）是对的，而且足够支撑你想要的全部场景。 分野不在「是不是 HTML」，在契约把真相放在哪。
② 你的四个诉求分散在四个契约层上，必须分开建
批注回写是 L2（真相在文件+补丁），版本回滚是 L2 的延伸，决策卡片是 L4（真相在协议/队列）， 图显前置实时编辑是 L3（真相在结构化模型）。想用一套东西兜住四件，就是在做完整 GUI。
③ 「实时交互」不必然导致成本攀升，「多人协作」才会
单人单机的实时拖拽，成本约是批注方案的 2-3 倍；一旦加上账号、权限、并发、审计，贵一个数量级（人日 → 人月）。 拐点在协作，不在实时。这直接回答了你的成本疑问。
④ 最锋利的一条参考不是 HTML 工具，恰恰是绕开 HTML 的那个
EditHere 的自我定位是「不依赖 DOM，屏幕上看得到就能标」。它反证了：HTML 的通用性有域界， 真正全域通用的是「语义锚 + 像素锚」双轨。纯 HTML 方案在网页域赢，跨域要靠坐标兜底。
⑤ 你点名的四件参考，实际是三件开源 + 一件内部能力
dsh-raw-html 存在（94★）；dsh-html-workbench 无同名项目，等效物是 dsh-workbench 与 DSH-better-sidebar——这个名字没被占用，建议留给你自己的插件； EditHere 存在（228★）；WorkBuddy 的人机双写未见公开文档，是内部实现， 但交互模型可从截图逆向（见 §4）。这反而说明：这一层还没有标准答案，谁先抽出来谁定标准。
01 / 命题

通用性不是来自「能画界面」，是来自「能降级」

2026 年有一批人在说「Markdown 已死，HTML 当立」——Anthropic 工程师的文章、中文技术圈的转述、 以及 HtmlRAG 那类论文（HTML 比纯文本更适合建模文档结构）。这些都对，但都只说了半句。

1.1四性：HTML 真正稀缺的地方

Markdown、JSON、GenUI 协议各缺一角，只有 HTML 四角俱全：

能力HTMLMarkdownJSON 模型GenUI 协议
人可读（无需工具）是 浏览器即读是 纯文本否 需渲染器否 需宿主
机可写（LLM 直出）是 训练充分是 最省 token中 易出错括号中 需守 schema
可版本化（diff / git）是 文本行 diff是 行 diff 最干净中 需语义 diff否 无持久产物
零依赖渲染是 任何设备有浏览器中 需 md 渲染器否否 绑宿主版本
可升级为「应用」是 加 JS 即应用否中 看渲染器是 但不可归档

关键的第五行。Markdown 不能往上长成应用；JSON 不能往下退成文档； GenUI 卡片能交互但会话一关就没了。只有 HTML 同时站得住两头—— 因为 Web 的原始设计哲学就是渐进增强（progressive enhancement）。

同一份文件，从「只读报告」到「可批注」到「可拖拽」到「可当应用」，是四种加载模式，不是一个产品线。

这正是你说的「轻成本方案也 OK，但更希望实时」的可行路径

所以你想的「先静态批注、以后再实时」不是妥协，是同一条路上往前走一格。 文件不用换、版本库不用迁、批注资产不浪费。这是 HTML 相对 GenUI 的结构性优势： GenUI 的升级是换产品，HTML 的升级是加一层 <script>。

1.2但通用性有域界——这是 EditHere 教我的

EditHere 的 README 里有一句极清醒的话，比任何「HTML 万能」的论述都有价值： DOM 批注（它点名了 Codex、WorkBuddy 侧栏、Agentation）「对网页很高效，但画面一旦离开 DOM （游戏、桌面软件、视频、AI 生成的图）就无从下手」。

也就是说，它的存在本身就是对强命题的反驳。但它的做法给了一个更好的答案： 把批注降到「无损原图 + 像素坐标 + 布局变更」这个更底层的契约上，就能通吃 网页、Qt/WPF/Electron、手游画面、Canvas/HUD、AI 生图、视频帧。

由此得到一条设计法则
做「HTML 内批注」时，锚定不要只用 CSS selector。语义锚（selector + 文本引用）负责让 AI 找得到代码， 像素锚（rect + 视口）负责让人找得到位置。两个都存，任一失效另一兜底——这是跨域通用的最小代价。

1.3三类界面的分工判据

这张图能直接回答你「适合各个领域」的疑问：不是 HTML 适合所有领域，是「思考」这件事在所有领域都发生。 写研报、评审架构、复盘项目、拆解竞品——无论哪个行业，这一步都在「读一份东西然后说哪里不对」。 HTML 抓的是这个横切面，不是行业。

02 / 分层

四种契约，四种成本结构

这不是成熟度阶梯，是四个不同的东西。混着谈，就会得出「必须做完整 GUI」的错误结论。

2.1四层的真相归属，决定了工程量

层真相住在哪人怎么改AI 怎么改典型工程量冲突风险
L1 只读HTML 文件本身不改，只看整篇重写 0（用现成渲染器）无
L2 批注HTML 文件 + 批注 JSON选区/点选 + 写文字读批注 → 定点改 3-5 人日中 锚点漂移
L3 直接操作结构化模型（JSON/AST），HTML 只是渲染结果拖拽/缩放/属性面板改同一个模型 +5-7 人日低 同源即无冲突
L4 决策卡协议消息 + 决策队列，UI 是临时视图点按钮 / 填备注生成选项与影响 2-3 人日（自造 DSL）
0.5-1 人月（对齐 A2UI）		高 视图与状态不同步

注意第三行的转折：L3 之所以「冲突风险低」，唯一原因是人机改的是同一个模型。 这不是技术细节，是架构分水岭。用 span rewrite（dsh-web-design 的做法）把人的编辑写回源码， 解决的是「保留注释格式」；但 AI 下次整篇重写时，人的手工编辑照样会被覆盖。 只有模型同源，才能真正做到「AI 重写不覆盖人的改动」。

这也是你要警惕的滑坡
一旦决定「HTML 里的东西要实时可改」，下一步很自然就是「那所有块都模型化吧」， 再下一步就是「那干脆做个编辑器产品吧」——这就是你说的「为了实时交互开发了 GUI 完整前端后端」的那条路。 阻断它的唯一办法：按块判定「改的是数据还是像素」（见 §7）。

04 / 批注层

批注要补两个维度：意图，和设计令牌

你现在的痛点不是「不能批注」——WorkBuddy 已经能了。痛点是批注完 AI 只能逐条改， 于是生成一大堆碎片化修订，你看不过来。

4.1锚定 × 意图，两个正交维度

现有实现只标了「锚在哪」（选区 / 元素 / 整段）。但 AI 真正需要知道的是「为什么改」—— 因为不同意图走完全不同的执行路径：

意图类型典型批注AI 的执行路径合并策略
内容纠错「这句结论和上一节矛盾」重写该文本块全部合并为一次重写
结构调整「这两节顺序反了」移动/重排块合并为一次结构操作
视觉调整「表格太挤」「这个紫太亮」改 CSS / 设计令牌合并为一次令牌替换
补充信息「这里缺一个成本数字」需要外部检索或问你串行，需先取数
存疑待议「这个判断我不确定」不改，转成决策项升级为决策卡（§6）
删除「这一段不要」删块合并

「存疑待议」这一行是关键。你现在截图里那张「三处需你判断」的表格，本质上是 AI 把手写批注 里的存疑项整理成了文本；如果批注本身带意图类型，这些项可以自动汇总成决策卡， 不需要 AI 再写一遍。这就是 §4 和 §6 的接口。

4.2三重锚定 + 降级链

单一锚点一定会漂：只用 selector，AI 重写后 class 变了就丢；只用文本引用，改一个字就丢； 只用坐标，窗口一缩就丢。工业级做法是三个都存，按序降级： 

{
  "doc": "四引擎总纲.html",
  "docHash": "sha256:9f2c…",        // 版本对齐，防错版
  "block": "分野",                  // 块级归属，支持局部回滚
  "anchor": {
    "selector": "[data-block='分野'] .tbl tr:nth-child(3)",   // ① 结构锚
    "textQuote": { "exact": "可审察上限", "prefix": "3.4.3 的", "suffix": "——" }, // ② 文本锚
    "rect": [812, 436, 210, 24],     // ③ 视觉锚（像素，跨域兜底）
    "viewport": [1440, 900]
  },
  "intent": "structure",             // 内容/结构/视觉/补充/存疑/删除
  "note": "这一节的表格太挤，建议拆成两张",
  "priority": "should"
}

降级链：selector 命中 → 文本模糊匹配（前后文各 32 字）→ 偏移量近似 → rect 交集 → 交给人工确认。 任一层命中就继续，全失败则不静默丢弃，而是回问「第 3 条批注找不到了，它原本指这段：…，还改吗？」 ——这一条很重要，静默丢弃是批注系统最伤人的失败模式。

4.3设计批注要单独走令牌，别混进内容

你明确提到「也可以针对网页设计本身批注」。这件事不能用内容批注的通道，否则 AI 会去逐处改 CSS， 造成十几处零散改动、下次重写又全部还原。正确做法是升到令牌层： 

{
  "intent": "design-token",
  "token": "--jade",
  "from": "#6fd6c4",
  "to": "#7fe0cf",
  "scope": ".pill--jade, .hero em, figure .darr",   // 影响面先算给你看
}

这样一次批注 = 一次全局令牌替换，而不是 N 处局部修补。 你在截图里那个 HTML 之所以"配色协调"，就是因为它是令牌驱动的——这个优势应该被批注系统利用，而不是被它破坏。

最小可行动作
不用重写 WorkBuddy 的批注 UI。只要做两件事：① 在批注 chip 上加速度选择「这是什么问题」； ② 在发送时按意图分组打包。AI 侧再按分组分别执行。改动量在几十行级别，收益是「一次修订」代替「十次修订」。
05 / 版本器

git 做骨，块索引做肉

你的诉求是「不只有最新版本覆盖全部，要可回滚，甚至局部回滚」。 这句话里藏着一个技术难点：HTML 是整篇文件，git 的 diff 是行级的，两者不对齐。

5.1三档粒度，只有中间那档值得做

粒度实现能回答的问题工程量评价
文件级每轮存 v3.html + git commit 「回到第 2 版」0（现成） dsh-workbench 已有面板，直接用。但你要的局部回滚做不到

5.2块级版本库的结构

5.3三个必须钉死的约定

  1. 块 id 不可变。AI 每次重写整页时最容易丢 data-block。解法是把「保留既有 block id， 只改块内内容」写进生成契约，并在宿主侧做自检即拒绝：提交前比对 manifest，发现丢块就报错退出， 而不是静默合并。（你那个 build-doc.mjs 的"超宽直接退出"就是这个思路，复用它。）
  2. 分支语义 = 方案语义。不要拿分支做「版本号」。分支应该是「方案 A / 方案 B」， tag 是「定稿 v1」。这样并行评审天然成立：两份 HTML 并排看，选一个 merge。
  3. 正文用 git，批注用本地。不要把正文塞进 CRDT（Yjs/Automerge）。 实时协同很诱人，但代价是「真相变成二进制状态」，HTML 从此不可 git、不可邮件、不可归档—— 正好毁掉 §1 里那个唯一优势。批注层可以 CRDT，正文层必须文件。
轻量模式：把批注内嵌进 HTML 自己
如果要发给外部评审（对方没有版本库），可以把批注与版本指针塞进 <script type="application/kb-annotations+json">。 这样一个文件 = 正文 + 批注 + 版本指针，可邮件、可微信、可归档。 代价是文件变大、需要剥离步骤。这是 Markdown 和 JSON 都做不到的事，是 HTML 独有能力，值得留一个开关。
06 / 决策卡片

从「消息内嵌 UI」到「决策一等公民」

你说「甚至作为弹窗通知组件出现在显控大屏或工作台，而非仍是局限在特定会话界面的对话框输入」。 这一句其实已经指出了架构：决策不该属于会话，决策该属于项目。

6.1Decision Bus：一份 JSON，多个视图

为什么必须这样？因为如果决策卡只是「消息里的一坨 HTML」，它有三个死法： ① 会话滚过去就找不到了；② 换设备要重新生成；③ 无法被大屏/待办这些非会话端消费。 反过来，只要决策是项目里的一份 JSON，卡片就只是它的一个渲染器——你可以今天用 HTML 渲染， 明天换成 A2UI，后端一个字都不用动。

顺便一个结构性呼应
你 KunPeng-Ops 的「显控引擎」五段闭环是观 → 图 → 演 → 令 → 证，第 04 步「令」的产物写的正是 「决策卡」。所以这件事不是新造概念，而是把文档里那张静态表格升格为有状态对象。 你原来的设计已经预见了它，只是还没给它状态。

三个设计原则，缺一个就会退化成「好看的表格」：

  1. 必须可降级为文本。不支持渲染的环境（邮件、企微、纯文本 agent）要退化成你截图 3 那种表格。 这是 HTML/DSL 相对纯 GenUI 的结构性优势——别为了卡片丢掉这个退路。

6.3技术选型：先自造，后对齐

MCP Apps（SEP-1865）3-5 人日中高（iframe 沙箱限制）想立刻在 WorkBuddy 里跑，且能接受沙箱
A2UI0.5-1 人月高（原生组件、跨端）要做成产品、给别人用的时候

关键建议：自造 DSL 的 payload 结构照抄 A2UI 的 shape（surface + components + dataModel + actions）。 这样将来迁到 A2UI 只是换渲染器，不用重写 AI 侧的生成逻辑。这是"低成本起步、不锁死未来"的标准做法。

07 / 图显前置

四类图分治：改的是数据，还是像素

这是你最关键的疑问——「是否意味着成本攀升，为了实时交互 HTML 开发了 GUI 完整前后端」。 答案取决于一句话：你拖的那个东西，本质是数据还是像素。

图类型结构度真相放哪方案人日为什么
工作计划 / 甘特高JSON（任务+时间+依赖） 模型驱动2 拖的是时间条 = 改数据，天然可校验、可回滚
工作流 DAG高JSON（节点+边） 模型驱动 + 拖拽3-4 拖节点 = 改边，还能实时检测成环/孤立节点
架构图 / 关系图中Mermaid / 文本描述 半模型1 文本↔图双向，人在图上加减节点即可
预期效果图 / 对标图低位图 批注 + 局部重绘1 不能拖。只能圈出来说"这里改"，走 EditHere 式批注 + inpaint
这一句话省掉一个 GUI
效果图不该做实时拖拽编辑器。它没有结构，做出来就是个画图软件，投入产出比极差。 正确做法是「圈选 + 一句话 + 局部重生成」——这正是你说的"轻成本方案"，而且它不是妥协，是正解。

7.1模型驱动的最小闭环

这个闭环里最重要的不是渲染器，是 patch(model) 这一步——把一次拖拽翻译成语义变更 （{"op":"move","from":[2,1],"to":[3,1]}），而不是翻译成坐标。 一旦人的操作是语义的，它就和 AI 的操作同构，两者可以 merge、可以 diff、可以一起回滚。

代价也要说清楚
模型驱动的隐性成本在双向同步：model 改了要重渲染，DOM 改了要回写 model。 做不好就是「拖完跳回去」的鬼畜体验。所以只对值得的两类图做（甘特、DAG）， 且第一版可以偷懒：拖完不即时回写，等「保存」时一次性 patch。省掉双向同步，省掉一半工程量。
08 / 成本账

攀的不是「实时」，是「协作」

这是你问题里最实际的一问。给三档具体的数，你就知道该停在哪。

档组成人日要后端吗能做到做不到
A · 批注补丁 Agentation 或自写 overlay + payload schema + 宿主解析 + 意图分组 3-5 否 局部/板块/全局/设计批注，统一提交，一次修订 实时预览、拖拽

给你的判断建议
做 A + B 的一部分，明确不做 C。理由是：你现在的使用场景是「一个人 + 一个 AI 反复磋商」， 不是「一个团队在同一个文档上并发编辑」。后者的真实需求（权限、审计、冲突合并）你现在一个都没有， 为它付一个数量级的成本，是最典型的过度设计。等真的有三个人要同时改同一份报告时再说。
09 / 路线

五个阶段，每阶段有验收线

按你的习惯，每阶段给「产物 + 验收 + 回滚条件」。不过关不进下一步。

阶段做什么产物验收标准不过怎么办
P0 · 1-2 天 定批注 payload schema（含意图维度、三重锚定） annotation.schema.json 拿现有的一份 HTML 报告，手工写 5 条批注 JSON，AI 能只按 JSON 完成修订且不误伤其他块 说明锚定设计有问题，回到 §4.2 改降级链
P1 · 3-5 天 版本器：data-block 切片 + manifest + 块级 diff + 回滚命令 kb-version 脚本 能对一份 11 块报告执行 rollback --block X --to vN，其余 10 块 hash 不变 若块 id 频繁丢失，先解决生成契约，不进入 P2
P2 · 2-3 天 决策总线 + 卡片渲染器（自造 DSL，shape 照 A2UI） decisions/*.json + <kb-decision> 一次提交 3 项决策，状态落盘；关掉会话重开，卡片仍能读到并显示已决/待定 若不能脱离会话恢复，说明还停在「消息内嵌 UI」，重做存储层
P3 · 5-7 天 只做甘特 + DAG 两类图的模型驱动（含拖拽 + 保存时 patch） plan.model.json + 渲染器 拖动一个节点 → 保存 → 重开 → 位置保持；AI 改同份 model 后，人的改动仍在 若双向同步做不稳，降级为「保存时 patch」，砍掉实时回写
P4 · 3-4 天 抽成 DSH 插件三件套（见 §10） dsh-html-workbench 在干净的 DSH 环境里 dsh plugin add 后全流程可用，不依赖你本地特殊配置 若依赖过重，说明耦合没切开，回退只做脚本不做插件

合计 14-21 天（比我前面说的 8-11 人日多，因为含了 P4 的工程化）。 如果只到 P3，8-12 天，已经覆盖你全部四个诉求。

10 / 插件

如果做成 DSH 插件：只做中间层

你问「是否考虑完整开发图显前置 HTML 编辑器的 DSH 插件」。值得做，但不要做编辑器—— 编辑器已经有三个人在做了，你做的是它们之间那道缝。

10.1三件套

dsh-html-workbench
├─ host/     Node 服务：文件读写 · 块索引 · 版本库(git) · 决策队列
│            通信照 dsh-workbench 的做法：HTTP + SSE 增量推送
├─ client/   浏览器 overlay：批注层 · 版本时间轴 · 决策卡渲染
│            批注层可直接复用 agentation（零依赖 React）
└─ skill/    教 AI 三件事：怎么读批注 payload · 怎么按块重写 ·
             怎么把存疑项吐成决策卡 JSON

10.2三条边界，决定它能不能被别人组合

  1. 不接管渲染——复用 dsh-raw-html。它已经把 HTML 变界面了，你不要重写。
  2. 不接管文件树——复用 DSH-better-sidebar 或 dsh-workbench 的侧栏底座。
  3. 不接管元素编辑——复用 dsh-web-design 的 span rewrite 能力。

只做「人与 AI 之间的协商层」：批注怎么收集、版本怎么切、决策怎么落。这一层现在没人做， 而它恰好是三条地基之间唯一的真空。耦合最低的插件，最容易被别人组合使用；什么都做的插件，没人敢装。

命名建议
dsh-html-workbench 这个名字检索无占用，且语义准确（HTML + 工作台）。 但它容易被误认为是「又一个侧边栏」。若想更准确，可考虑 dsh-html-review（强调评审） 或 dsh-coauthor（强调人机双写）。名字里带 review 或 coauthor，比带 workbench 更能说清它不是编辑器。
11 / 批判

五个还没解决的问题，别当它不存在

一份只给方案不给风险的研究是失职。以下都是我没能解决、或业界也没解决的。

① 块之间的耦合
回滚「分野」这一块到 v5，但 v7 的「底座」引用了 v6 才有的一个概念——回滚后引用会断。 要么做依赖声明（块级 import），要么接受「回滚后人工核对」。我倾向前者，但那是另一个人日的事。
② 块 id 的稳定性没有强保证
「保留既有 block id」只能靠生成契约 + 宿主自检。AI 仍可能「理解性地」重排结构从而丢掉 id。 自检能拦住静默损坏，但拦不住 AI 真的想重构。这时需要显式的「允许改结构」二次确认。
③ MCP Apps 沙箱弹不出系统通知
iframe 沙箱里没有 Notification 权限，所以你设想的「决策卡作为弹窗通知出现在大屏」， 不能靠卡片自己实现，必须走宿主侧（Decision Bus + 宿主监听）。这也是为什么 §6 坚持要总线。
④ 未验证项
dsh-raw-html 的「VCP 视觉通感协议」规范细节未公开； A2UI 在 WorkBuddy/DSH 这类宿主上的实际落地未实测； Agentation 与 DSH 侧栏的 iframe/沙箱兼容性未实测。这三项都是"看文档像可行"，没有跑过。
⑤ 「HTML 全域通用」这个说法本身要收一收
你在提问里说「适合各个领域」。我理解你的意思是「不限于某一行业」，这没问题。
但如果理解成「不限场景」就错了：移动端、即时通知、高频操作、需要权限的协作，HTML 都赢不了。 准确的说法是：HTML 是「思考与评审」这一横切面的通用范式，不是所有交互的通用范式。 把边界说清楚，方案才不会变成"什么都要做"。
