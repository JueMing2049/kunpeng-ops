01 / 摘要

五条结论，先给判断先说五句大白话

这一节可以独立成篇。后面每一节都是这五条的展开与证据。 后面看不懂没关系，记住这五句就够用了。

①
强命题不成立，弱命题成立

HTML 承载一切领域交互是错的；但「唯一同时做到人可读、机可写、可版本化、零依赖渲染的交付契约」是对的，且足够支撑全部场景。分野不在「是不是 HTML」，在契约把真相放在哪。 能看、能改、能存档，三样都占的格式，眼下只有网页。别的要么只能看，要么存不下来。关键不在「是不是网页」，在「改完之后，那份东西到底存在哪」。

②
四个诉求分散在四个契约层上

批注回写是 L2，版本回滚是 L2 延伸，决策卡片是 L4，图显前置实时编辑是 L3。想用一套东西兜住四件，就是在做完整 GUI。 你想要的四件事，其实是四种不同的活儿。想一次全干，等于要盖一栋楼；分开干，一个人三五天就够。

③
「实时交互」不必然导致成本攀升，「多人协作」才会

单人单机实时拖拽约是批注方案的 2-3 倍；加入账号、权限、并发、审计后贵一个数量级（人日 → 人月）。拐点在协作，不在实时。 贵的不是「能实时改」，是「好几个人同时改」。一个人用，贵两三倍；一群人用，贵十倍。

④
最锋利的参考恰恰是绕开 HTML 的那个

EditHere 用「不依赖 DOM，屏幕上看得到就能标」反证了 HTML 的通用性有域界。真正全域通用的是「语义锚 + 像素锚」双轨。 有个叫 EditHere 的工具干脆不用网页，改用截图加坐标。因为它发现：一离开网页，网页那套办法就完全不管用了。这句话反过来给网页划了条边界。

⑤
你点名的四件参考，实际是三件开源 + 一件内部能力

dsh-raw-html 存在（94★）；dsh-html-workbench 无同名项目——名字空着，建议留给你自己的插件；EditHere 存在（228★）；WorkBuddy 人机双写是内部实现。这一层还没有标准答案，谁先抽出来谁定标准。 你点名的四样，三样是别人开源做好的，一样是 WorkBuddy 自家的。说明这块地还没人占——连名字都空着，谁先做谁定规矩。

展开：为什么第 ⑤ 条是好消息
四件参考的核实结果说明，「人与 AI 之间的协商层」目前是真空： dsh-raw-html 只管渲染，dsh-workbench / DSH-better-sidebar 只管工作台与 Git， dsh-web-design 只管元素编辑回写。没有一件处理「批注怎么收集、版本怎么切、决策怎么落」。 所以你不必与现存生态竞争，只需与它们组合。
02 / 命题

通用性不是来自「能画界面」，是来自「能降级」网页真正厉害的地方，是它能「往后退」

2026 年有一批人在说「Markdown 已死，HTML 当立」——Anthropic 工程师的文章、中文技术圈的转述、以及 HtmlRAG 那类论文。这些都对，但都只说了半句。 这两年流行一句话：「别写 Markdown 了，直接写网页。」这话对，但只说了一半。

常被忽略的一点 第五行「可升级为应用」才是关键。Markdown 长不成应用，JSON 退不成文档，GenUI 会话一关就没了。只有 HTML 两头都站得住。

2.1四性：HTML 真正稀缺的地方

Markdown、JSON、GenUI 协议各缺一角，只有 HTML 四角俱全： 四种格式摆一起比，高下立刻分明——看最后一行就行：别的格式要么长不成应用，要么一关就没了。

能力HTMLMarkdownJSON 模型GenUI 协议
人可读（无需工具）是 浏览器即读是 纯文本否 需渲染器否 需宿主
机可写（LLM 直出）是 训练充分是 最省 token中 易出错括号中 需守 schema
可版本化（diff / git）是 文本行 diff是 行 diff 最干净中 需语义 diff否 无持久产物
零依赖渲染是 任何设备有浏览器中 需 md 渲染器否否 绑宿主版本
可升级为「应用」是 加 JS 即应用否中 看渲染器是 但不可归档

同一份文件，从「只读报告」到「可批注」到「可拖拽」到「可当应用」，是四种加载模式，不是一个产品线。

因为 Web 的原始设计哲学就是「渐进增强」——这正是 v2 这一版自身的实现原理

所以「先静态批注、以后再实时」不是妥协，是同一条路上往前走一格。文件不用换、版本库不用迁、批注资产不浪费。GenUI 的升级是换产品，HTML 的升级是加一层 <script>。 所以「先做批注、以后再实时」不叫妥协，是同一条路往前走一格。稿子还是那份稿子，底稿不用重抄，批注也不用重写。换别的方案等于换产品，网页的方案只是多带一个脚本。

2.2但通用性有域界——EditHere 教我的

EditHere 的 README 里有一句极清醒的话：DOM 批注（它点名了 Codex、WorkBuddy 侧栏、Agentation）「对网页很高效，但画面一旦离开 DOM（游戏、桌面软件、视频、AI 生成的图）就无从下手」。它把批注降到「无损原图 + 像素坐标 + 布局变更」这个更底层的契约上，于是通吃网页、Qt/WPF/Electron、手游画面、Canvas/HUD、AI 生图、视频帧。 EditHere 的说明里有一句话特别清醒——它说，网页上那种批注（还点名了 Codex、WorkBuddy 侧栏）确实好用，但画面一离开网页（游戏、桌面软件、视频、AI 画的图）就完全没辙。于是它换了条路：不认网页元素，只认「这张原图 + 这几个坐标」。就这一换，游戏、桌面、视频、生图全能标了。

由此得到一条设计法则
锚定不要只用 CSS selector。语义锚（selector + 文本引用）让 AI 找得到代码，像素锚（rect + 视口）让人找得到位置。两个都存，任一失效另一兜底。 所以圈位置要存两套：一套给 AI 看（按结构定位，它才知道改哪行代码），一套给人看（按坐标定位，换台设备也不会指错）。哪套失效，另一套顶上。

2.3三类界面的分工判据

这能直接回答「适合各个领域」的疑问：不是 HTML 适合所有领域，是「思考」这件事在所有领域都发生。写研报、评审架构、复盘项目、拆解竞品——这一步都在「读一份东西然后说哪里不对」。HTML 抓的是这个横切面，不是行业。 这也回答了你说的「适合各个领域」：不是网页适合所有行业，是「读一份东西、说哪里不对」这件事在所有行业都发生。写报告、审架构、复盘项目、拆竞品——全是这个动作。网页抓的是这个动作，不是行业。

03 / 分层

四种契约，四种成本结构四层不是四代人，是四种东西

这不是成熟度阶梯，是四个不同的东西。混着谈，就会得出「必须做完整 GUI」的错误结论。 便签、草稿、白板、会议表决器——你不会说表决器比便签高级。这四层也是。把它们当成「一代比一代强」，就会误以为必须造最后一层。

3.1四层的真相归属，决定了工程量

层真相住在哪人怎么改AI 怎么改工程量冲突风险
L1 只读HTML 文件本身不改，只看整篇重写0无
L2 批注HTML 文件 + 批注 JSON选区/点选 + 写文字读批注 → 定点改3-5 人日中 锚点漂移
L3 直接操作结构化模型（JSON/AST），HTML 只是渲染结果拖拽/缩放/属性面板改同一个模型+5-7 人日低 同源即无冲突
L4 决策卡协议消息 + 决策队列，UI 是临时视图点按钮 / 填备注生成选项与影响2-3 人日 / 0.5-1 人月高 视图与状态不同步

L3 冲突风险低，唯一原因是人机改的是同一个模型。用 span rewrite（dsh-web-design）写回源码，解决的是「保留注释格式」；AI 下次整篇重写时，人的手工编辑照样被覆盖。只有模型同源才能真正避免。 第三层之所以最不容易打架，原因只有一个：人和 AI 改的是同一份东西。别的方法是把你的修改「贴」回原文——贴得再小心，AI 下次整篇重写时照样盖掉。

这也是要警惕的滑坡
「HTML 里的东西要实时可改」→「所有块都模型化」→「干脆做个编辑器产品」，这就是「为了实时交互开发 GUI 完整前后端」的那条路。阻断它的唯一办法：按块判定「改的是数据还是像素」（见 §08）。 「这块要能改」→「那全都做成能改的」→「干脆做个编辑器卖吧」——这就是通往「为一句话写一整套系统」的滑坡。刹车只有一个：每块单独问一句「你改的是数据还是图片」（见 §08）。

05 / 批注层

批注要补两个维度：意图，和设计令牌红笔要补两样：说清「为什么改」，和「改哪里」

痛点不是「不能批注」——WorkBuddy 已经能了。痛点是批注完 AI 只能逐条改，生成一堆碎片化修订。 批注这件事 WorkBuddy 已经能做了。真正的麻烦在批注之后：AI 一条一条改，改出一堆碎片，你根本看不过来。

5.1锚定 × 意图，两个正交维度

意图类型典型批注AI 的执行路径合并策略
内容纠错「这句结论和上一节矛盾」重写该文本块合并为一次重写
结构调整「这两节顺序反了」移动/重排块合并为一次结构操作
视觉调整「表格太挤」改 CSS / 设计令牌合并为一次令牌替换
补充信息「缺一个成本数字」需外部检索或问你串行，先取数
存疑待议「这个判断我不确定」不改，转成决策项升级为决策卡（§07）
删除「这一段不要」删块合并

「存疑待议」是关键接口：你截图里那张「三处需你判断」的表格，本质是 AI 把手写批注里的存疑项整理成文本；批注若自带意图，这些项可自动汇总成决策卡，不需要 AI 再写一遍。

5.2三重锚定 + 降级链

{
  "doc": "四引擎总纲.html",
  "docHash": "sha256:9f2c…",        // 版本对齐，防错版
  "block": "分野",                  // 块级归属，支持局部回滚
  "anchor": {
    "selector": "[data-block='分野'] .tbl tr:nth-child(3)",   // ① 结构锚
    "textQuote": { "exact": "可审察上限", "prefix": "3.4.3 的", "suffix": "——" }, // ② 文本锚
    "rect": [812, 436, 210, 24],     // ③ 视觉锚（像素，跨域兜底）
    "viewport": [1440, 900]
  },
  "intent": "structure",
  "note": "这一节的表格太挤，建议拆成两张",
  "priority": "should"
}

降级链：selector → 文本模糊匹配（前后文各 32 字）→ 偏移量近似 → rect 交集 → 人工确认。全失败则不静默丢弃，而是回问「第 3 条批注找不到了，它原本指这段…还改吗？」——静默丢弃是批注系统最伤人的失败模式。 找不到位置怎么办：先按结构找，找不到就按原文那句话找，再不行按它大概在第几屏找，最后才问你。任何一层都不许悄悄丢掉——批注系统最伤人的失败，就是你写了十条，它默默执行了七条。

5.3设计批注要单独走令牌

{
  "intent": "design-token",
  "token": "--jade",
  "from": "#6fd6c4",
  "to": "#7fe0cf",
  "scope": ".pill--jade, .hero em, figure .darr"   // 影响面先算给你看
}

这样一次批注 = 一次全局令牌替换，而不是 N 处局部修补。你那份 HTML 配色协调，正因为它是令牌驱动的——这个优势应被批注系统利用，而不是被它破坏。 改颜色别说「这里这个绿不对」，要说「把'绿'这个变量从 A 换成 B」。一次换全套，而不是挨个地方打补丁。你那份 HTML 之所以看着协调，就是因为它所有颜色都取自同一张色表——这个优势别被批注搞坏。

最小可行动作
不重写批注 UI，只做两件事：① chip 上加「这是什么问题」的速选；② 发送时按意图分组打包。改动几十行，收益是「一次修订」代替「十次修订」。
06 / 版本器

git 做骨，块索引做肉把稿子存成「分页档案」，别每次整本重印

难点在于：HTML 是整篇文件，git 的 diff 是行级的，两者不对齐。 难点在这：网页是一整篇，git 是按行比对的，两者对不上。所以「退回某一节」这种操作，现成工具做不到。

粒度实现能回答的问题工程量评价
文件级每轮存 v3.html + git commit「回到第 2 版」0（现成）dsh-workbench 已有面板，但局部回滚做不到
块级data-block + 内容 hash → 块快照字典「把'分野'回到 v2，其他保持 v5」2 人日推荐。同时解决局部回滚与 AI 重写漂移
字符级diff-match-patch 存 patch「把这句话里的'不'字改回去」5 人日+过度工程

6.1三个必须钉死的约定

01
块 id 不可变

AI 重写整页最易丢 data-block。把「保留既有 id，只改块内内容」写进生成契约，宿主侧做自检即拒绝：比对 manifest 发现丢块就报错退出（复用你 build-doc.mjs「超宽直接退出」的思路）。 每条内容的「页码」不能变。AI 整篇重写时最爱把页码弄丢——所以要在生成时就规定死，并且提交前自动核对，少了一个就报错退出，而不是默默合并。

02
分支语义 = 方案语义

分支不是「版本号」，是「方案 A / 方案 B」；tag 是「定稿 v1」。并行评审天然成立：两份 HTML 并排看，选一个 merge。 分支别拿来当版本号。一个分支 = 一个方案（方案甲、方案乙），定稿了才打一个「v1」的标签。这样同时评两套方案，就是并排看两份稿子，挑一份。

03
正文用 git，批注用本地

不要把正文塞进 CRDT（Yjs/Automerge）。实时协同的代价是「真相变成二进制状态」，HTML 从此不可 git、不可邮件、不可归档——正好毁掉 §02 那个唯一优势。 别为了「多人实时改」把正文塞进协同编辑的数据库。那样一来稿子就变成一堆看不懂的数据，不能比对、不能发邮件、不能存档——恰好把网页唯一的优势毁掉。

轻量模式：把批注内嵌进 HTML 自己
发给外部评审时，把批注与版本指针塞进 <script type="application/kb-annotations+json">，一个文件 = 正文 + 批注 + 版本指针，可邮件、可微信、可归档。这是 Markdown 和 JSON 都做不到的事。
07 / 决策卡片

从「消息内嵌 UI」到「决策一等公民」决定不该锁在聊天窗口里

你说「甚至作为弹窗通知组件出现在显控大屏或工作台」——这一句已经指出架构：决策不该属于会话，决策该属于项目。 你说「能不能做成弹窗，出现在大屏或工作台上」——这句话其实已经说出答案了：决定该跟着项目走，不该跟着聊天窗口走。

7.1Decision Bus：一份 JSON，多个视图

如果决策卡只是「消息里的一坨 HTML」，它有三个死法：① 会话滚过去找不到；② 换设备要重新生成；③ 无法被大屏/待办这些非会话端消费。反过来，只要决策是项目里一份 JSON，卡片就只是它的一个渲染器——今天用 HTML，明天换 A2UI，后端一个字不用动。 如果决定只是一条聊天消息，它会死三次：翻上去就找不着、换台设备就得重发、大屏和待办根本读不到它。但只要决定存在项目里，卡片就只是它的一个「外壳」——壳可以换，里面的东西不动。

一个结构性呼应
KunPeng-Ops 显控引擎五段闭环是观 → 图 → 演 → 令 → 证，第 04 步「令」的产物写的正是「决策卡」。这不是新造概念，而是把文档里那张静态表格升格为有状态对象——原设计已预见它，只是还没给它状态。

7.2这一版把静态示意换成了真卡（可点）

原报告这里只有一张画出来的示意卡；v2 换成三张可点选、可写备注、可导出 JSON 的决策卡。选完点「导出决策 JSON」即可把结果交给下游——这正是本报告论证的「L4 契约」自己的示范。

08 / 图显前置

四类图分治：改的是数据，还是像素先问一句：你拖的是数据，还是图片

「是否意味着成本攀升」的答案取决于一句话：你拖的那个东西，本质是数据还是像素。 「是不是要为此写一整套前后端？」——答案全看你拖的是什么。拖的是「第三周挪到第四周」，那是改数据；拖的是「这张效果图里的人往左一点」，那是改图片。两件事的成本差十倍。

图类型结构度真相放哪方案人日为什么
工作计划 / 甘特高JSON（任务+时间+依赖）模型驱动2拖时间条 = 改数据，可校验、可回滚
工作流 DAG高JSON（节点+边）模型驱动 + 拖拽3-4拖节点 = 改边，可实时检测成环
架构图 / 关系图中Mermaid / 文本半模型1文本↔图双向，加减节点即可
预期效果图 / 对标图低位图批注 + 局部重绘1不能拖，只能圈出来说"这里改"
这一句话省掉一个 GUI
效果图不该做实时拖拽编辑器——没有结构，做出来就是画图软件。正确做法是「圈选 + 一句话 + 局部重生成」，不是妥协，是正解。

8.1模型驱动的最小闭环

最重要的不是渲染器，是 patch(model)——把一次拖拽翻译成语义变更而不是坐标。人的操作一旦是语义的，就和 AI 的操作同构，可以 merge、diff、一起回滚。 关键不是画得好看，是把「我把它挪了一下」翻译成「第 3 步挪到第 2 步」，而不是「x 从 120 变成 80」。变成「第几步」之后，它就和我改的东西是同一种语言，可以合并、可以比对、可以一起退回去。

代价也要说清楚
隐性成本在双向同步：model 改了要重渲染，DOM 改了要回写 model，做不好就是「拖完跳回去」。所以只对甘特、DAG 做，且第一版偷懒：拖完不即时回写，保存时一次性 patch。省掉一半工程量。

12 / 批判

五个还没解决的问题五件我还没搞定的事

只给方案不给风险是失职。以下都是我没能解决、或业界也没解决的。 只讲方案不讲风险，是耍流氓。下面这五条，我也想不出好办法。

① 块之间的耦合
回滚「分野」到 v5，但 v7 的「底座」引用了 v6 才有的概念——引用会断。要么做块级依赖声明，要么接受「回滚后人工核对」。
② 块 id 的稳定性无强保证

③ MCP Apps 沙箱弹不出系统通知
iframe 里没有 Notification 权限，所以「决策卡作为弹窗通知出现在大屏」不能靠卡片自己实现，必须走宿主侧 Decision Bus。这正是 §07 坚持总线的原因。
④ 未验证项
dsh-raw-html 的 VCP 规范细节未公开；A2UI 在 WorkBuddy/DSH 上的落地未实测；Agentation 与 DSH 侧栏的 iframe 兼容性未实测。三项都是「看文档像可行」，没跑过。
⑤ 「HTML 全域通用」这个说法本身要收一收
你在提问里说「适合各个领域」，理解成「不限于某一行业」没问题；理解成「不限场景」就错了——移动端、即时通知、高频操作、需要权限的协作，HTML 都赢不了。准确说法：HTML 是「思考与评审」这一横切面的通用范式，不是所有交互的通用范式。把边界说清楚，方案才不会变成「什么都要做」。
